# Протокол сессия ↔ сервер

## 1. Задача и ограничения

Скилл запускает локальный сервер объяснения PR и браузер. Вызвавшая сессия агента становится воркером: выполняет задачи сервера через CLI. Сервер не вызывает модель самостоятельно и не требует от харнеса входящих RPC, субагентов или специальных хуков. Достаточно запуска shell-команд.

## 2. Топология

Браузер общается с сервером по REST и SSE. Агент получает работу через pull-команду `devflow-diff-explain worker next`. Очередь, объяснения, история вопросов и патчи сохраняются на диске. Один сервер обслуживает один ключ PR; одна сессия владеет слотом воркера.

SSE начинается со снимка `state`, затем передаёт ревизии `route` и `chat` и обновления состояния. Треды коллег и ревью-прогресс не подписываются и не передаются. Поля прежних версий в схемах совместимости не означают наличие соответствующих сервисов.

## 3. CLI `devflow-diff-explain`

| Команда | Назначение |
|---|---|
| `up --pr <key-or-url>` | Найти или поднять сервер, зарегистрировать сессию, открыть UI и начать работу |
| `up --local <path> [--base <ref>]` | Объяснить локальный diff относительно базы |
| `worker next --pr <key>` | Дождаться задачи и получить инструкцию, контекст и команду сдачи |
| `task complete <id> --file <path> --pr <key>` | Сдать результат из UTF-8 файла |
| `task progress <id> --text <text> --pr <key>` | Обновить статус длинной задачи |
| `task fail <id> --reason <text> --pr <key>` | Явно отказаться от задачи с причиной |

Ключ, выданный `up`, передаётся во всех дальнейших командах. CLI сам находит манифест, токен и идентификатор воркера. Тексты CLI и заданий — английские. Маркеры `stop the loop` и `DONE` завершают рабочую петлю; точное поведение закреплено в инструкции скилла и её тестах. Сервер после завершения петли может продолжать обслуживать сохранённый разбор.

## 4. Формат задачи

Канон — схемы в `packages/protocol/src/task.ts`, `messages.ts` и `json-schema.ts`. Задача содержит `id`, `type`, `priority`, `attempt`, `instructions`, абсолютные пути `contextFiles` и при необходимости `resultSchemaFile`.

| Тип | Результат и контекст |
|---|---|
| `route.skeleton` | Краткое описание и план смысловых блоков; методичка и сохранённый дифф; схема `readableSkeletonResult` |
| `route.section` | Пояснения назначенных блоков/файлов и важных строк; тот же дифф и принятый план; схема `readableSectionResult` |
| `route.diagram` | Схема окружающего потока данных или запрос ограниченного контекста; собственная схема результата |
| `chat` | Ответ Markdown на явный вопрос; закреплённые объяснение, версия и выбранный код |
| `echo` | Служебная проверка петли, доступная только в режиме разработки |

`review.feedback` остаётся распознаваемым в сохранённой очереди для безопасного обновления, но сервер такие задачи не создаёт и при старте отменяет открытые старые задачи этого типа.

Каждая задача самодостаточна: память агентской сессии не является частью контракта. Общие методички и диффы лежат в `payload/shared`, разовый план — в каталоге генерации, вопрос — в отдельном каталоге чата. Имена и пути сохранённого контекста не заменяются содержимым текущего checkout.

Основной контекст диффа ограничен 320 КиБ. Патчи урезаются целиком с явной пометкой; список файлов остаётся полным. Индекс отдельных полных патчей позволяет агенту дочитать нужный файл той же версии. Контекст схемы ограничивается отдельно. Каталоги состояния приватные (0700), файлы payload — 0600.

## 5. Очередь

Приоритет `interactive` обгоняет `background`; внутри класса действует FIFO. Вопросы чата интерактивны, генерация объяснения фоновая. Одна задача арендуется одному воркеру; TTL — 600 секунд для интерактивной и 1800 для фоновой. Протухание возвращает работу в очередь, максимум — три попытки. Отмена сохраняет факт, что воркер ещё держит контекст, до его следующего обращения.

Результат ограничен 256 КиБ. Структурные и предметные ошибки отклоняются fail-closed с пояснением для пересдачи; число отклонений ограничено. Повторная сдача закрытой задачи не применяет результат второй раз. Результат отменённой задачи не изменяет актуальное объяснение.

Очередь фиксирует принятый результат транзакционно. Оркестраторы применяют его к своему состоянию и восстанавливают незавершённое применение при сверке после сбоя или рестарта.

## 6. Постепенная готовность

После плана доступны описание и структура блоков. Одна задача заполняет назначенные блоки согласованным рассказом; точечный повтор может заполнить один блок. Схема потока данных выполняется отдельно, её сбой не переводит готовые файлы в ошибку. `task progress` передаёт краткий статус, ответ чата приходит целиком.

## 7. Живость воркера и переподключение

Регистрация новой сессии перехватывает слот и возвращает аренды прежнего владельца в очередь. Чужая сессия получает `worker_conflict` до выполнения операции. Открытый long-poll поддерживает живость; окно по умолчанию — 240 секунд, CLI повторяет ожидание сам. Молчание с арендой и срок аренды учитываются отдельно.

Уход последнего SSE-клиента дольше 60 секунд позволяет закончить петлю, когда открытой работы не осталось. Перезагрузка страницы или краткий обрыв сети не завершают работу немедленно. Остановка сервера обрывает ожидающие соединения и закрывает подписки до БД.

## 8. Discovery и безопасность

Манифест — `~/.sherpa/servers/<prKey>.json`: ключ PR, PID, порт, адрес UI, bearer-токен и версии. По умолчанию сервер слушает `127.0.0.1` на случайном порту. `/healthz` открыт для проверки discovery; API требует токен. Только SSE принимает его в query, поскольку `EventSource` не позволяет задать заголовок. Статика UI не содержит секретов.

Манифест занимается атомарно. Живой сервер повторно используется; протухший манифест освобождается после проверки владельца. Источники кода доступны рантайму через интерфейс `ReviewSource` только для чтения. Запись комментариев, вердиктов, отметок ревью и фидбека не входит в работающий API.

## 9. Версии и сохранённые данные

Версия протокола задаётся в `packages/protocol/src/version.ts`. В линии 0.x несовпадение minor несовместимо; после 1.0 граница — major. Ломающее изменение воркерского сообщения или задачи требует повышения версии протокола.

Версия формата объяснения и эпоха задания проверяются отдельно: старый сохранённый текст можно читать, но продолжать незавершённую генерацию по устаревшему формату нельзя. Старые таблицы БД и схемы совместимости не удаляются вместе с runtime-сервисами. Названия `review*`, `sherpa/<id>` и каталог `.sherpa` местами сохранены для совместимости.
