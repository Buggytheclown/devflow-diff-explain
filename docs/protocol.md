# Протокол сессия↔сервер

Скилл запускается в агентском харнесе ревьюера (Claude Code, Codex и другие — зоопарк), поднимает локальный сервер и браузер-UI. Вызвавшая сессия остаётся жить как **воркер**: выполняет ИИ-задачи (генерация маршрута, заполнение остановок, чат), которые ставит UI.

## 1. Задача и ограничения

Ограничения, из которых следует весь дизайн:

1. **От сессии можно требовать только одного: умения запускать шелл-команды.** Никаких субагентов, хуков, MCP — это есть не во всех харнесах.
2. **У сессии нет входящего интерфейса** — сервер не может ей «позвонить». Единственная модель — pull.
3. **Инструменты запуска команд в харнесах имеют таймауты** (Claude Code: дефолт 2 минуты, максимум 10). Вечно блокирующий вызов будет убит харнесом, и мы об этом не узнаем.
4. **Сессия смертна и прерываема** в любой момент; прервать её извне мы тоже не можем.
5. **Агенты склонны повторять команды и ошибаться в форматах** → идемпотентность и валидация на границе обязательны. Отсюда же снисходительность разбора аргументов: `sherpa/42` вместо `42`, кавычки и бэктики вокруг меток (`parseTaskId`, `sanitizeLabel` в `packages/cli/src/args.ts`).

## 2. Топология

```
браузер-UI ⟷ (REST + SSE, bearer-токен) ⟷ локальный сервер ⟷ (CLI `sherpa`, pull) ⟷ агентская сессия
                                                │
                                                └── диск (~/.sherpa + состояние per-PR): SQLite (очередь,
                                                    снапшоты, черновики, история чата) и payload-файлы
```

Два канала с разной природой:

- **UI ↔ сервер** — обычный веб. REST для действий, SSE для реактивности: статусы очереди, появление остановок маршрута, синхронизация комментариев хоста ревью. Ничего специального.
- **Сессия ↔ сервер** — pull через CLI. Всё нетривиальное — здесь, разделы ниже про него.

Раскладка состояния и хранилище — `docs/architecture.md`.

## 3. CLI `sherpa`

Тонкий клиент, распространяется вместе со скиллом одним самодостаточным `.mjs`; рядом лежит модуль сервера, который CLI грузит только в `devflow-diff-explain server`. Зачем не голый `curl`:

- **Поиск сервера и авторизация зашиты внутрь** — агенту не нужно знать ни порт, ни токен;
- **контракт версионируется** в одном месте, а не размазан по промптам скилла;
- **вывод форматируется как промпт для модели**, а не как JSON для парсинга.

| Команда | Семантика |
|---|---|
| `devflow-diff-explain up` | Бутстрап сессии: поднять сервер ревью (или найти живой по манифесту), зарегистрироваться воркером, напечатать ссылку на UI и следующий шаг петли. `--local <path>` вместо `--pr` поднимает ревью рабочего дерева каталога проекта, `--base <ref>` задаёт, с чем его сравнивать, `--verdicts <instruction>` заменяет Comment на Ship и Request changes и передаёт поручение пользователя на исход ревью, которое задача `review.feedback` с вердиктом повторит агенту. Сервер стартует фоновым демоном и переживает выход CLI (`packages/cli/src/up.ts`). При холодном старте открывает браузер, если не передан `--no-open`. |
| `devflow-diff-explain server` | Процесс сервера PR: его демонизирует `up`, модели он не нужен. Аргументы уходят модулю сервера как есть. |
| `devflow-diff-explain worker register` | Только регистрация сессии воркером PR — для переподключения к уже поднятому серверу. |
| `devflow-diff-explain worker next` | Ждёт задачу без срока и возвращается только с задачей, `done` или ошибкой. Внутри — цикл обычных long-poll запросов на серверном окне `LONG_POLL_DEFAULT_SECONDS` = 240 с: ответ `idle` CLI глотает и сразу шлёт следующий запрос. Окно в запросе не передаётся. Каждый запрос — признак жизни; пока он висит, признак — само открытое соединение (§7). Выдаёт задачу в аренду. |
| `devflow-diff-explain task complete <id> --file <path>` | Сдать результат. Сервер валидирует fail-closed при приёме; при ошибках печатает их списком в промпт-формате — «исправь и вызови complete снова». Повторный complete по закрытой задаче — no-op. |
| `devflow-diff-explain task progress <id> --text "<msg>"` | Дешёвая статусная отметка; UI показывает «агент работает: …». Срок аренды она не продлевает. |
| `devflow-diff-explain task fail <id> --reason "<msg>"` | Явный отказ (нет доступа, не хватает контекста). Задача уходит в состояние ошибки с причиной, видимой в UI. |

Флаги: `--pr <key>` у всех команд (иначе `SHERPA_PR`, иначе PR текущей ветки arc-чекаута — `packages/cli/src/pr-discovery.ts`); `--local <path>`, `--base <ref>` и `--verdicts <instruction>` только у `up` (`--local` несовместим с `--pr`, путь обязателен, `--base` и `--verdicts` — только вместе с `--local`; поручение непустое и не длиннее `VERDICTS_INSTRUCTION_MAX_CHARS` = 2000 символов); `--harness`, `--model`, `--lang <ru|en>` у `up` и `worker register` (метки сессии для статуса воркера и подсказка языка UI); `--no-open` только у `up`. Полный разбор — `parseArgs` в `packages/cli/src/args.ts`, справка — `helpText` в `format.ts`.

**Что читает модель.** Вывод — инструкция, а не данные: задача в промпт-формате с путями к контексту и готовыми командами сдачи (`formatTask`), ссылка на UI и следующий шаг (`formatUpReady`), ответы сервера как есть, `DONE` отдельной строкой в конце работы (`formatDone`). Тексты ошибок сервера человекочитаемы; CLI дописывает к ним следующий шаг там, где он из сообщения не следует (`NEXT_STEP_BY_CODE`).

**Коды возврата.** 0 — любой штатный протокольный ход, включая отклонение результата валидатором: это диалог с моделью, а не сбой, и агент читает stdout, а не коды. 1 — всё, после чего команда не состоялась: кривые аргументы, провал discovery, RPC-ошибка сервера, локальный отказ по размеру результата.

**Лимит результата на стороне CLI.** `task complete` проверяет размер файла до отправки (`readResultFile`, `RESULT_MAX_BYTES` = 256 КБ) и отбивает перебор локально: задача остаётся в аренде, и у модели есть попытка сократить файл. Дойди тот же результат до сервера — задача закрылась бы ошибкой (§5).

**Инструкция сессии** — `packages/skill/SKILL.md`: вывести PR-ключ из аргумента вызова, запустить `up`, показать ссылку ревьюеру, дальше крутить `worker next` и следовать выводу, пока не придёт `DONE`. Там же — правила петли: ожидание не стоит ни одного хода модели — `worker next` запускается в фоне с пробуждением по завершении, если харнес это умеет, иначе на переднем плане одним блокирующим вызовом с явным суточным таймаутом тула, без опросов и статусов между; прерванное пользователем ожидание — повод запустить его снова; останов только по `DONE` или по явному «stop the loop»; ни одна задача не завершается молча — либо `complete`, либо `fail --reason`; файлы из каталога `shared/` между задачами не меняются и читаются один раз за сессию.

## 4. Формат задачи

Вывод `next` — готовый промпт, модель читает его глазами: строка `TASK sherpa/<id> (<тип>), attempt <n>`, инструкции, список файлов контекста, путь к схеме результата (если есть) и команды сдачи.

Путь к файлу результата выбирает CLI, а не модель: `<os.tmpdir()>/sherpa-<uid>/<prKey>/<сессия>/<taskId>-<attempt>.json` (у задач без схемы — `.md`), где сессия — хеш `SHERPA_DIR` и `workerId`. Путь уникален для аренды, поэтому в `complete` уходит только записанное в этой попытке.

Принципы:

- **Тяжёлый контекст — файлами, не в stdout.** Сервер материализует диффы, планы и историю чата в markdown-файлы под `~/.sherpa/prs/<prKey>/payload` (каталоги 0700, файлы 0600) и даёт абсолютные пути.
- **Каждая задача самодостаточна**: сессия могла умереть и переподключиться — задача не опирается на память сессии, весь нужный контекст в payload. Память сессии — бонус (кэш понимания PR), не контракт.
- **Схема результата — часть задачи**: у структурных задач в payload лежит путь к JSON-схеме, и модель предупреждена, что приёмка валидируется.

**Типы задач** — `taskTypeSchema` в `packages/protocol/src/task.ts`: `echo` (фиктивная задача для прогона петли — единственное, что ставится ручкой `enqueue`), `route.skeleton` (выжимка + план остановок + порядок тура), `route.section` (заполнение остановок плана), `chat` (вопрос ревьюера с контекстом выделения), `review.feedback` (раунд опубликованных комментариев локального ревью: агент правит код и отвечает в тредах). Перегенерация после нового пуша — те же `route.*` с дополнительным контекстом, отдельных типов нет. Неизвестный тип отбивает валидация.

**Payload по типам.**

| Тип | Контекст |
|---|---|
| `route.skeleton` | методичка, дифф PR, файлы перегенерации (если есть); схема результата `routeSkeletonResult` |
| `route.section` | то же плюс план с помеченными целевыми остановками; схема результата `routeSectionResult` |
| `chat` | методичка, дифф PR или сторона файла под якорем, текст вопроса, патч выделения, контекст маршрута, история чата; схемы результата нет — ответ markdown |
| `review.feedback` | `feedback.md`: вердикт раунда, каталог проекта и каждый тред — абсолютный путь файла, сторона со строкой, фрагмент патча и переписка; схема результата `reviewFeedbackResult` |

Схемы генерируются из канонов zod (`generateJsonSchemas` в `packages/protocol/src/json-schema.ts`), путь едет полем `resultSchemaFile`.

**Общий и разовый контекст.** Неизменное между задачами живёт в `payload/shared` (`packages/server/src/shared-payload.ts`): методички и дифф PR по ключу `<base>-<head>`. Разовое — в каталоге генерации маршрута (`payload/route/gen-…`, новая генерация сносит прежние), в каталоге вопроса чата (`payload/chat/<uuid>`, свой на каждый вопрос и повтор) и в каталоге раунда ревью (`payload/feedback/<roundId>`). Каталоги, которые не держит ни одна живая задача, сервер сносит при старте и по ходу работы.

**Бюджет контекста.** Сервер собирает файл контекста под байтовый потолок: дифф PR и общий файл чата — `CONTEXT_BUDGET_BYTES` = 320 КБ (`packages/server/src/route-payload.ts`), контекст перегенерации — 128 КБ на интердифф и по 64 КБ на прошлый маршрут и на новые треды, история чата — 8 последних обменов по 8 КБ. Механика — `fitPayloadFiles` и `fitText` в `packages/server/src/payload-budget.ts`: приоритет задаёт порядок спеков, под ещё не собранные файлы остаётся минимум.

Урезание всегда помечено в тексте, чтобы модель не считала обрезок полным: `[TRUNCATED: …]` на месте выброшенного, `[UNAVAILABLE: …]` там, где контекста нет вовсе (бинарный файл, хост не дал патч). В диффе PR режутся целые патчи файлов, а не хвосты: первыми уходят сгенерированные, последними — тесты, внутри ранга — самые большие; список изменённых файлов и шапка PR не режутся никогда. Что осталось за бортом, UI показывает отдельно (`UiGenerationCap`).

## 5. Очередь

Реализация — `packages/server/src/queue.ts`.

- **Lease, не dequeue.** `next` выдаёт задачу в аренду с TTL по классу приоритета: `LEASE_TTL_SECONDS` = 600 с у интерактивных, 1800 с у фоновых. Аренда истекла (воркер умер молча) → задача возвращается в очередь и тратит попытку. Протухание ленивое: очередь проверяет аренды на входе в каждую операцию, отдельного таймера нет.
- **Попытки.** `MAX_TASK_ATTEMPTS` = 3. Исчерпаны — задача уходит в `failed` с причиной, видимой в UI, и в очередь не возвращается.
- **Два класса приоритета.** Интерактивные (`chat`, `review.feedback`) всегда обгоняют фоновые (`route.*`) — ревьюер ждёт у экрана. Внутри класса FIFO по id, вытеснения уже выданной задачи нет.
- **Отмена.** UI может снять задачу: ждущая в очереди закрывается сразу, выданная в аренду помечается отменённой, но воркер узнаёт об этом только при следующем вызове CLI (прервать его нельзя — ограничение №4), получая `noop` с текстом «задача отменена, делать нечего». Пока он не отозвался, UI честно показывает, что агент ещё занят отменённой задачей.
- **Идемпотентность на каждой ручке.** Повторный `complete`/`fail`/`progress` по закрытой задаче — `noop` с понятным текстом; `next` при живой аренде возвращает ту же задачу без нового TTL и не тратит попытку («доделай начатое»); задача не в аренде у вызывающего — `lease_not_held`.
- **Приёмка fail-closed.** Результат проверяет приёмщик типа задачи (`route-orchestrator.ts`, `chat-orchestrator.ts`, `feedback-orchestrator.ts`) синхронно, в транзакции `complete`. Отклонение — не ошибка RPC: ответ `rejected` со списком ошибок, аренда остаётся у воркера, попытка не тратится. Отклонений на одну аренду три; на третьем задача закрывается ошибкой, сырой вывод сохраняется и доступен из UI. Отдельный исход — «сервер не может проверить прямо сейчас» (дифф не пережил рестарт): воркеру уходит тот же список с оговоркой, что попытка не потрачена, в хранилище не меняется ничего.
- **Лимиты.** Результат больше `RESULT_MAX_BYTES` = 256 КБ закрывает задачу ошибкой (`result_too_large`, HTTP 413) — до валидации, потому его и отбивает CLI заранее (§3). Тело запроса ограничено `REQUEST_BODY_MAX_BYTES` = 1 МБ (`packages/server/src/http.ts`): потолок взят с запасом над лимитом результата, чтобы умеренный перебор доехал до очереди и закрыл задачу по существу, а не отбился как кривой запрос. Текст `progress` — `PROGRESS_TEXT_MAX_CHARS` = 500, длиннее отбивает схема.
- **Последовательность — гарантия протокола, а не запрет параллелизма**: один воркер держит одну аренду; внутри задачи харнес волен параллелить субагентами.

## 6. Прогрессивность

Токен-стриминг из чужой сессии через шелл-команды нереалистичен. Вместо него:

- **Гранулярность задач**: маршрут = `route.skeleton` плюс `route.section` на группу остановок. UI оживает после скелета и наполняется по мере приёмки секций — это и есть прогрессивный показ. Секции — независимые задачи, то самое место, где харнес с субагентами может их параллелить.
- **`task progress`** для длинных задач — статусные строки в UI.
- Ответ чата приходит целиком одним `complete`.

## 7. Живость воркера и переподключение

Каждый вызов CLI — признак жизни, но живость сервер считает не по одной тишине: обрыв соединения — сильный сигнал, тишина — слабый. Воркер жив, пока выполнено хотя бы одно (`packages/server/src/worker-registry.ts`):

1. **открыто его воркерское соединение** — простаивающий воркер висит в `worker next` сколько угодно долго (CLI перезапрашивает long-poll сам), и убитую сессию ОС выдаёт закрытием сокета немедленно;
2. **он держит аренду задачи** и молчит меньше `WORKER_DEAD_AFTER_SECONDS` = 360 с (но не дольше срока самой аренды) — во время выполнения задачи модель законно молчит минутами;
3. без соединения и аренды — молчит меньше `WORKER_GAP_GRACE_SECONDS` = 60 с: это пауза между возвратом одного `next` и следующим вызовом.

Иначе сервер помечает воркера мёртвым → UI переходит в состояние «агент отключён» (читалка работает, ИИ-зоны деградируют, инструкция переподключения — `docs/product.md`). Убитая простаивающая сессия видна за минуту; убитая во время выполнения задачи — за шесть (сервер не отличает «убит с арендой» от «работает молча»).

**Переподключение и вытеснение**: новая сессия всегда права. Ревьюер запускает скилл → скилл находит живой сервер по манифесту (§8), не поднимает второй → регистрация свежей сессии перехватывает слот воркера, даже если прежний ещё жив. Очередь и состояние на диске — ничего не теряется: незавершённые аренды вытесненного возвращаются в очередь сразу (попытка тратится, как при протухании), его висящие long-poll принудительно будятся и получают `worker_conflict` — «останови петлю». Ждать признания смерти прежней сессии не нужно ни в каком сценарии. Сама регистрация `worker_conflict` не отдаёт никогда — его получает вытесненная сессия на своих следующих вызовах.

**Уход ревьюера.** UI-присутствие считается по живым SSE-подключениям (`packages/server/src/ui-presence.ts`): когда последнее закрыто дольше `UI_GONE_GRACE_SECONDS` = 60 с и в очереди нет ни ждущих, ни выданных задач, `next` отвечает `done` — сессия завершается. Грейс меньше минуты ставить нельзя: перезагрузка страницы, переход между вкладками, сон ноутбука и моргнувшая сеть рвут SSE на секунды, а это не уход. Машинного поля причины у `done` нет — только человекочитаемый текст: харнес ведёт себя одинаково при любой.

**Самоостановка сервера.** Команды `down` в контракте нет, поэтому сервер гасит себя сам после простоя (`packages/server/src/idle.ts`): `DEFAULT_IDLE_SECONDS` = 15 минут без открытых соединений и без запросов. Открытый SSE вкладки и висящий long-poll считаются занятостью, внутренние таймеры — нет. Состояние в SQLite остановку переживает, следующий `up` поднимает сервер заново. Порог перебивает переменная `SHERPA_IDLE_SECONDS` (0 — самоостановка выключена); она недокументированная, нужна сквозным тестам.

## 8. Discovery и безопасность

- Сервер на случайном порту и по умолчанию на `127.0.0.1`; `SHERPA_LISTEN_HOST=::` открывает его по IPv6 и IPv4. Манифест в `~/.sherpa/servers/<prKey>.json` хранит порт, имя для ссылки UI, PID, токен, версии протокола и сервера. Права файла 0600. Токен — 6 случайных байт (48 бит), base64url без padding, 8 символов (`packages/server/src/auth.ts`).
- Манифест публикуется атомарно: временный файл плюс `link`, занять путь может только один сервер. Живость чужого сервера проверяется не PID'ом, а `/healthz` с его же токеном — порт мог занять кто угодно.
- CLI определяет PR по cwd (или `SHERPA_PR` в env) → манифест → порт и токен. Агент не знает ни того, ни другого.
- **Токен обязателен для всех каналов**, включая UI. Локальная ссылка имеет вид `http://127.0.0.1:<порт>/#t=<токен>`; при внешнем слушателе используется имя виртуалки из манифеста. Фрагмент не уходит на сервер и переживает перезагрузку страницы; UI также читает старый `#token=` для живых серверов прежней версии (`packages/ui/src/fragment.ts`). SSE передаёт токен query-параметром `?token=` — `EventSource` не умеет заголовки; это единственное послабление, политика ручки — `bearer-or-query`.
- 48 бит достаточно для сервера, живущего часы: токен умирает вместе с процессом, а процесс гаснет по простою (§7). При 10⁴ проверок/с средний перебор занял бы около 450 лет, а по сети такой темп вдобавок заметно нагружает Node-сервер, поэтому отдельного ограничителя попыток по-прежнему нет. Сравнение токенов идёт по хешам за постоянное время.
- Принятый компромисс: при доступе через HTTP-прокси токен SSE из `?token=` оседает в его access-логах. Прямой HTTP-доступ и так не шифруется, а токен живёт не дольше сервера; кому этого мало — SSH-туннель до `127.0.0.1`, тогда и `SHERPA_LISTEN_HOST` не нужен.
- PR на github.com получает ключ `github-<владелец>--<репозиторий>--<номер>`: разделитель — удвоенный дефис, потому что в логине владельца его не бывает, а в имени репозитория бывает. Разбор: владелец — до первого `--`, номер — после последнего, репозиторий — всё между (`packages/protocol/src/pr-key.ts` — там же префиксы `arcanum-`, `local-<arc|git>-` и `github-`). Ссылку вида `https://github.com/<владелец>/<репозиторий>/pull/<номер>` (с любым хвостом) в ключ приводит CLI, до всех проверок: дальше по сессии едет уже нормализованный ключ, его же печатает `devflow-diff-explain up`.
- Локальное ревью ключа не имеет заранее: `up --local <path>` приводит путь к абсолютному через realpath, сам определяет VCS каталога (сначала спрашивает `arc`, потом `git`), берёт у неё корень чекаута и ветку и строит ключ `local-<arc|git>-<имя каталога>-<8 hex sha256(путь + ветка + база из `--base`)>`. Каталог, база и ветка уезжают серверу аргументами `--repo`, `--base` и `--branch` и сохраняются в `~/.sherpa/prs/<key>/local-host.json` (0600): перезапуск демона поднимается уже без флагов, а без файла и без флагов хоста нет. Поручение на исход ревью (`--verdicts <instruction>`) едет двумя путями: при холодном старте — аргументом `--verdicts <instruction>`, живому серверу — полем `localVerdicts` в запросе `register`, которое `up --local` шлёт всегда (`worker register` — никогда): строка — режим вердиктов с этим поручением, null — режим снят, нет поля — режим не трогается. Поручение сохраняется в `local-host.json` полем `verdicts` (строка или null). Побеждает последний `up`: другое поручение заменяет прежнее и тоже ложится на диск, без флага режим снимается. Применённое поручение сервер возвращает эхом `localVerdicts` в ответе; эхо не совпало с `--verdicts` — живой сервер старше CLI и поле отбросил, и `up` падает с просьбой его перезапустить, а не обещает вердикты, которых ревьюер не увидит.
- **Токен обязателен для всех каналов**, включая UI. Ссылка имеет вид `http://127.0.0.1:<порт>/#t=<токен>`: фрагмент не уходит на сервер и переживает перезагрузку страницы; UI также читает старый `#token=` для живых серверов прежней версии (`packages/ui/src/fragment.ts`). SSE передаёт токен query-параметром `?token=` — `EventSource` не умеет заголовки; это единственное послабление, политика ручки — `bearer-or-query`.
- 48 бит достаточно для сервера, живущего часы на loopback: при 10⁴ проверок/с средний перебор занял бы около 450 лет. Отдельного ограничителя попыток нет — этого запаса хватает. Сравнение токенов идёт по хешам за постоянное время.
- При холодном старте `devflow-diff-explain up` вызывает `open` / `xdg-open` / `start` напрямую, без shell: URL не попадает в историю команд, но кратко виден в argv opener-процесса. Компромисс принят для локальной машины: процесс короткоживущий, та же ссылка всегда печатается в stdout; `--no-open` отключает вызов.
- Протухшие манифесты — не прошедшие схему и оставшиеся от мёртвых процессов — чистятся при старте сервера, до заявки на свой манифест (`cleanStaleManifests` в `packages/server/src/manifest.ts`). CLI их не трогает.

## 9. Версионирование

Версия протокола — `PROTOCOL_VERSION` в `packages/protocol/src/version.ts`. Канон совместимости там же, `protocolVersionsCompatible`: в линии 0.x ломающим считается минор, с 1.0 достаточно совпадения мажора; нераспознанная строка несовместима.

Рукопожатие происходит на **каждом** воркерском запросе, а не только на первом: CLI не хранит состояние между запусками, а версии в теле стоят копейки (общая часть схем запросов — `messages.ts`). Несовместимость — ошибка `version_incompatible` с человеческим текстом «обнови скилл вместе с CLI и перезапусти сервер, они едут вместе»; её увидит и модель в выводе, и ревьюер в UI. Скилл с CLI и сервер деплоятся независимо, у большой команды разъезд версий гарантирован — ловим явно.

Отдельно версионируется дистрибутив скилла: `version.json` в корне каталога скилла, рядом с `bin/` (`distributionVersionSchema` в `packages/protocol/src/distribution.ts`). Сервер читает файл дистрибутива из trunk, сравнивает с зашитой версией и, если вышла новая, показывает в UI тост с фразой «что нового» и командой обновления — ничего не скачивает и не ставит сам (`packages/server/src/update-check.ts`). Результат проверки кэшируется на полчаса; отклонённая ревьюером версия помнится в настройках.

## 11. Закрытые вопросы

1. **Язык CLI.** Скриптовый рантайм, не компилируемый бинарник: TS, собранный esbuild'ом в один самодостаточный `.mjs`. CLI и сервер в одном монорепо делят типы и схемы контракта — рукопожатие и валидация не дублируются. Требования выдержаны: один файл, ноль внешних зависимостей в рантайме, проверка версии рантайма при старте с человеческой ошибкой (`packages/cli/src/runtime.ts`).
2. **Один сервер на PR или один на машину.** Per-PR: манифест на `prKey`, состояние на `prKey`, слот воркера один на сервер. Мультиплекса нет; лишние процессы гасит самоостановка по простою (§7).
3. **Где хранить долгоживущее состояние.** SQLite через встроенный `node:sqlite`, база на PR: очередь, снапшоты маршрута, история чата и черновики просятся в транзакции, а внешних зависимостей это не добавляет.
4. **Формат payload-контекста.** Markdown-файлы — модель читает их глазами; JSON-схема только на результат, и только у структурных задач (§4).
5. **Размер результата и обрезка контекста.** Результат — 256 КБ, с локальным отбоем на CLI до отправки; тело запроса — 1 МБ; контекст режется по байтовым бюджетам с явной пометкой урезанного (§4, §5).
