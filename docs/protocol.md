# Протокол сессия ↔ сервер

## 1. Граница ответственности

Агент работает в собственном харнесе, исследует PR/локальные изменения нативными инструментами и передаёт готовые байты. Приложение хранит снимки, проверяет связи архитектуры, блоков и всех файлов, показывает сохранённый код и ставит задачи по явным вопросам. Приложение не имеет PR/VCS-адаптеров, provider credentials и автоматического polling.

Канон — Zod в `packages/protocol`; модельный ввод, HTTP и сохранённые данные валидируются на границах. Payload-файлы доступны из локальной файловой системы; наличие пути не означает обязательного чтения моделью.

## 2. Топология

Сессия ↔ standalone CLI ↔ локальный HTTP/SSE сервер ↔ SQLite и браузер. Сервер сам LLM не вызывает. Пять файлов поставки: SKILL.md, agents/openai.yaml, version.json, CLI и сервер со встроенным UI. Состояние остаётся в `~/.sherpa`, SHERPA_DIR переопределяет корень.

## 3. CLI

```sh
DEVFLOW_CLI="$HOME/.agents/skills/devflow-diff-explain/bin/devflow-diff-explain.mjs"
node "$DEVFLOW_CLI" snapshot schema
node "$DEVFLOW_CLI" sources schema
node "$DEVFLOW_CLI" up --snapshot /absolute/export/snapshot.json --harness codex --model <model> --lang ru
node "$DEVFLOW_CLI" up --pr <saved-project> --code <codeSnapshotId> [--review <snapshotId>] [--view diff|route]
node "$DEVFLOW_CLI" snapshot import --pr <project> --file /absolute/export/snapshot.json
node "$DEVFLOW_CLI" sources import --pr <project> --file /absolute/export/sources.json
node "$DEVFLOW_CLI" worker next --pr <project>
node "$DEVFLOW_CLI" task complete <id> --lease <printed-ref> --file <result> [--next] --pr <project>
node "$DEVFLOW_CLI" task progress <id> --lease <printed-ref> --text <status> --pr <project>
node "$DEVFLOW_CLI" task fail <id> --lease <printed-ref> --reason <reason> --pr <project>
```

`up --snapshot` получает project из manifest, импортирует данные до регистрации worker и печатает ссылку с fragment-токеном. `--pr` обозначает сохранённый проект, не запускает чтение провайдера; --local/--base сообщают о переходе на импорт. Snapshot/sources import работают с запущенным сервером и не регистрируют новую модель. --no-open оставляет только ссылку. Worker next ждёт задачу; complete --next после сдачи продолжает ожидание. DONE и «stop the loop» завершают петлю.

Печатные команды содержат реальный абсолютный entry и shell quoting, включая пробелы и апострофы. Команда в PATH не требуется. CLI сохраняет grantToken из next и подставляет неизменный `--lease` reference конкретной выдачи во все команды; агент не управляет токеном. Старая команда не может получить токен более новой аренды того же taskId.

Ссылка нового импорта содержит `code=<codeSnapshotId>` ещё до обзора; `review=<snapshotId>` закрепляет конкретный разбор, `view` задаёт вид. При доступном экземпляре сервера старый URL A открывает A после импорта B, включая чистый профиль. После restart `up --pr ... --code ... --review ...` выдаёт новый авторизованный URL на тот же материал: прежний порт/токен не обязаны сохраняться.

## 4. Импорт кода

`code-snapshot/1`: project (локальный ключ из букв, цифр, точки, дефиса и подчёркивания), diffId, baseCommit/headCommit, capturedAt, pr (необязательные известные title/url/id/author/branches/state/updatedAt или null, без review-возможностей), полный files и дополнительные sources. Файл: path, changeType, oldPath, before/after (null только для отсутствующей стороны), patch (путь полного оригинала либо null для генерации), optional fileId/generated/hostFileUrl. CLI schema описывает вход: pr, sources, activate и поля файла со значениями по умолчанию можно опустить, их заполняет приложение. Артефакт: относительный file, kind text/binary/symlink/gitlink и известный mode. Gitlink сохраняет объект, symlink — байты цели без разыменования. Все изменённые файлы и существующие стороны обязательны; усечённого ready-снимка нет.

`code-sources/1`: project, codeSnapshotId, sources с path/revision/artifact. Ревизия — pinned base/head. У внешнего документа origin сохраняет URL, время, scope и известную исходную revision; байты сохраняются локальным артефактом в контексте этой версии кода. Источники дополняются, конфликтующие байты не перезаписываются. Один импорт кэширует чтение повторяющегося artifact path/kind/mode; следующий импорт читает файл заново и проверяет его заново.

Importer проверяет точные координаты строк патча, пути, отсутствие symlink escape, инвентарь и воспроизведение new из old+patch; hashes/sizes считает приложение. Временные файлы агента копируются в собственное хранилище приложения. codeSnapshotId отделён от snapshotId объяснения; diffId внутри проекта не может обозначить другие ревизии или байты. Полнота upstream PR и истинность ревизий относительно провайдера не могут независимо доказываться без запроса провайдера: агент экспортирует полный нативный инвентарь. Новая версия импортируется явно; activate:false и старый capturedAt не переключают активную версию.

HTTP получает только `{manifest: "/absolute/path/manifest.json"}`, сами байты идут из файлов вне лимита model result:

| Ручка | Результат |
|---|---|
| POST /api/snapshot/import | codeSnapshotId, diffId, число файлов/источников |
| POST /api/sources/import | тот же кодовый снимок с дополнительными источниками |
| GET /api/snapshot/raw?diffId=&fileId=&side=old\|new | полный оригинал стороны файла |
| GET /api/review/source?id= | сохранённый диапазон, hash, pinned revision, признак полного исходника |
| GET /api/snapshot/source?id= | полный импортированный источник, на который указывает диапазон |

Все ручки требуют локальный bearer. Ошибка до атомарной регистрации оставляет прежний читаемый снимок. Оригиналы не урезаются из-за preview или 256 КиБ результата. Чтение, restart и удаление экспортного каталога не требуют модели, сети или VCS. После импорта полного исходника прежний сохранённый диапазон получает доступ к полному файлу без повторного ответа агента. Отсутствующий материал даёт адресную недоступность без fallback и без новой задачи.

## 5. Задачи и результат

Task содержит id/type/priority/attempt, instructions, contextFiles и при необходимости resultSchemaFile. Все виды задач, включая чат по диапазону, получают target JSON с точной версией и указателями на патчи/оригиналы. Неизменный код и каталог источников кэшируются до форматирования. Продолжение даёт короткое назначение, ошибки и отдельную ссылку на принятый разбор для восстановления; читать весь контекст не требуется. Выданный путь результата и команда complete передают публикацию приложению.

Единственный текущий JSON-ввод подготовки: contractVersion:6 и overview, update, files. Первому checkpoint нужен overview: summary/evidence, flow и stops с архитектурными nodeIds, основными files и relatedFiles. Он может одновременно содержать пояснения всех файлов. Update меняет предметные поля; blocks редактирует блоки по ID, removeBlocks/blockOrder перегруппировывают. Каждый изменённый файл имеет одного основного владельца, затронутые узлы связаны с блоками. Связанные изменения проверяются атомарно; независимый файл принимается целиком. Файлы сдаются плоским массивом по путям, в любом порядке и любой полезной частью; annotations/example при отсутствии сохраняются. Evidence на входе — sources и optional limitation; внутренние claims модель не формирует.

Невалидная структура отклоняет смешанный checkpoint целиком; первая сдача не публикует файлы без принятых владельцев. На корректной структуре пофайловая ошибка, отсутствующий path или дубли отклоняют только соответствующие элементы. Partial-квитанция содержит сохранённые пути и необходимые исправления. Исчерпанное исправление не останавливает остальные файлы; последняя принятая версия читается и допускает адресный повтор. Пустая фиктивная summary для files-only не создаётся. Повтор схемы — тот же route.prepare.

Mermaid проверяется настоящим парсером: ID в подписи/комментарии не считается узлом. Приложение извлекает узлы/группы и подписи, агент задаёт связи блоков и только необходимые metadata. Рёбра адресуются ID и видом при неоднозначности. Writer не предлагает legacy context-ссылки, которые сервер не может разрешить. Ссылки проверяются по сохранённым версии/стороне/диапазону; попадание в изменённую строку не подменяет проверку истинности тезиса. Отчёт ошибки рендера v1 содержит snapshotId, diagramHash, viewIndex, reason и optional missingId. Устаревший отчёт не меняет новую схему. Локальная успешная отрисовка не создаёт дополнительную задачу или POST.

Чат возвращает непустой Markdown. Для кода: `[label](#code?path=URL_ENCODED_PATH&side=new&start=9&end=9)`; диапазон вне патча разрешается из импортированного полного источника. Приложение заменяет его стабильной `#source?id=<hash>` ссылкой. Недостающий источник импортируется агентом перед сдачей; приложение не читает его в провайдере. Ответ не принимается с недостоверной ссылкой. Явный вопрос закрепляет версию, вложение, показанное объяснение и историю; retry не подменяет материалы новым импортом.

UI отправляет `explanationRef` (reviewId/revision и версия) либо `codeRef` до готовности обзора. Текст объяснения получает сервер; лимит поля 40 000 символов не ограничивает вопрос по большому обзору. Файл или диапазон проверяется до постановки задачи. Показанное объяснение сохраняется один раз в обмене, идентичность кода и точный выбранный `historyText` — в `question_input`. Retry не пересобирает историю из текущей переписки. Новая запись не копирует прежние explanation.text/evidence; старый формат с history-массивом остаётся читаемым. Повреждённый либо невосстановимый legacy-вход не скрывает сам вопрос/ответ, но точный повтор отклоняется с явной причиной.

## 6. Очередь и восстановление

route.prepare — background, chat — interactive. Приоритет действует между арендами/checkpoint; приложение не прерывает выполняющийся процесс харнеса. Next возвращает lease с уникальным grantToken для каждой выдачи, в том числе повторной тому же worker. Complete/progress/fail передают этот токен автоматически через CLI. Worker-регистрация передаёт слот новой сессии. Необратимые статусы — done/failed/cancelled; поздний чужой результат не применяется. Структурный route.prepare ограничен 16 МиБ UTF-8, остальные результаты — 256 КиБ. Только complete имеет увеличенный предел HTTP-тела с учётом JSON escaping. Оригиналы по-прежнему импортируются отдельно.

Документ/ответ, done, привязки и квитанция записываются в общей SQLite-транзакции. Retry возвращает квитанцию без повторного применения. Вложенное исключение отменяет общую запись, даже если перехвачено внешним кодом. После commit публикуются память и уведомления; сбой одного listener не отменяет запись и не подавляет остальные. Доменные ошибки-значения сохраняют необходимые счётчики. Незавершённые задачи и budget исправлений переживают restart.

Подготовка учитывает N=2+B+F единиц: описание, архитектура, блоки и файлы. До принятого обзора знаменатель неизвестен. Сохранённый результат читается при ошибке/отмене новой подготовки; готовность относится к текущей подготовке. Ошибка Mermaid допускает повтор обычным checkpoint. Настройки генерации отделены от фиксированного русского Arcanum dark UI; первый рендер не ждёт GET settings.

## 7. Живость и безопасность

Long-poll поддерживает живость worker; CLI продолжает idle-ожидание самостоятельно. Молчание с арендой и уход UI учитываются отдельно. Уход последнего SSE-клиента дольше grace позволяет завершить петлю после закрытия работы. Остановка закрывает ожидающие соединения/подписки до БД.

Discovery manifest содержит prKey/PID/port/token/versions, создаётся атомарно; живой сервер повторно используется. API требует bearer, только SSE принимает token в query. Fragment-токен показывается пользователю, не публикуется в сторонних системах. Сервер по умолчанию слушает loopback. Provider credentials приложение не ищет и не использует.

## 8. Совместимость

Protocol 0.27, эпоха задания 9. В 0.x несовпадение minor несовместимо; worker/server/UI обновляются согласованно. Новая сессия не принимает bare overview/flow, legacy stops или внутренние claims. Старые rows остаются читаемыми, но их исполнители не возвращаются. Unversioned legacy, v2–v6 и explanation/1 читаются без перегенерации; новые разборы хранятся как explanation/2 с одним порядком блоков и отдельными файловыми пояснениями. Новая эпоха перевыдаёт незавершённую подготовку на исходном diff с сохранением принятых файлов. Неизвестная более новая схема БД отклоняется до первой записи.

Исторические migrations, таблицы и пользовательские байты не удаляются. Миграция 030 добавляет `code_artifact_aliases`: старый непрозрачный `image.blobId` указывает на проверенный SHA-256 оригинала. Совместимый импорт сохраняет старый ID изображения; конфликт MIME/сторон/размеров, существующего локального blob либо alias отклоняет всю транзакцию. После restart изображение читается по старому ID без экспорта. Прежний неполный кэш не объявляется полным: доступны уже сохранённые материалы, явный импорт той же версии проверяет прежние ревизии/инвентарь и сохраняет ID/patch для существующих ссылок. Новый импорт не переписывает прежние вопросы. Canonical blobs не зависят от GC временного payload.
