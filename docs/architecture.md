# Архитектура Шерпы

Система: из чего собрана, как данные ходят между частями, что хранится на диске и какие правила держатся во всём коде. Контракты живут в `packages/protocol` — здесь только смысл и границы. Протокол сессия↔сервер описан отдельно: `docs/protocol.md`.

## 1. Состав: пакеты и роли

pnpm-монорепо, семь пакетов, TypeScript везде, Node ≥ 22.13.

| Пакет | Роль |
|---|---|
| `@sherpa/protocol` | Zod-схемы и типы всего, что пересекает границы: задачи и сообщения RPC, доменная модель ревью, интерфейс `ReviewHost`, снапшот маршрута, ручки и события UI, манифест discovery, лимиты и версия протокола. Кода с побочными эффектами нет — только схемы и чистые проверки |
| `@sherpa/server` | Демон одного PR: HTTP-слой, очередь задач с арендами, хост-адаптеры, оркестраторы маршрута и чата, валидатор результатов, хранилище |
| `@sherpa/ui` | Веб-интерфейс ревьюера: React 19, сборка Vite |
| `@sherpa/cli` | Единственный исполняемый файл `sherpa`, которым пользуется агент; он же поднимает сервер командой `devflow-diff-explain server` |
| `@sherpa/skill` | Дистрибутив для харнеса: `SKILL.md` и `bin/` с командой и модулем сервера |
| `@sherpa/fixtures` | Фикстурный хост и детерминированные данные: дев-режим, галерея состояний, e2e, замер производительности |
| `@sherpa/e2e` | Сквозные сценарии на Playwright и замер производительности |

**CLI** собирается esbuild в один самодостаточный `.mjs`: рантайм-зависимостей нет, встроенного `fetch` и стандартной библиотеки хватает.

**Сервер** собирается тем же способом в один ESM-модуль `devflow-diff-explain-server.mjs`, и статика UI зашита прямо в него. Модуль при импорте ничего не исполняет — сервер поднимает его экспорт `runServer(argv)`. `packages/server/build-server.mjs` читает `packages/ui/dist` и подменяет модуль `src/ui-assets.ts` картой «путь внутри сборки → содержимое в base64». В исходниках эта карта пуста намеренно: дев-запуск раздаёт UI с диска, дистрибутив — из памяти, ветвлений по режиму в коде нет.

Хранилище стоит на встроенном `node:sqlite`. Отсюда и порог версии Node, и возможность собрать сервер в один файл: нативных зависимостей у него нет.

Модуль SQLite грузится по требованию через `createRequire`, а не статическим импортом: иначе старый Node падал бы сырой ошибкой линковки до того, как `checkNodeVersion` (`packages/server/src/runtime.ts`) объяснит человеку, что делать. Порог — 22.13 либо 23.4: в линейку 22 модуль бэкпортировали раньше, чем он появился в 23-й, поэтому 23.0–23.3 старше 22.13, но модуля там ещё нет.

**Дистрибутив скилла** — каталог `packages/skill/dist`: `SKILL.md`, `bin/devflow-diff-explain.mjs`, `bin/devflow-diff-explain-server.mjs`, `version.json`. Именно `dist` линкуется в харнес, исходники туда не попадают.

Команда одна — `sherpa`, файлов два. Исполняемый только `devflow-diff-explain.mjs`; модуль сервера CLI грузит `import()` по пути, вычисленному в рантайме, и только в `devflow-diff-explain server` — поэтому esbuild не тянет сервер в бандл CLI, а петля агента, которая дёргает CLI на каждый вызов, сервер с зашитым UI не грузит. `devflow-diff-explain up` спавнит демона как `node <флаги рантайма> <devflow-diff-explain.mjs> server …` и передаёт ему найденный модуль в `SHERPA_SERVER_BIN`. Флаги рантайма демона (сейчас `--use-system-ca`) задаёт композиционный корень CLI (`packages/cli/src/index.ts`), ядро `up` лишь отбрасывает те, которых текущий Node не знает. Версия поставки одна на оба файла — поле `version` корневого `package.json`.

Шрифты IBM Plex едут в поставке: приезжают npm-пакетами и попадают в сборку (`packages/ui/src/styles/fonts.css`), сеть во время работы не нужна — закрытый контур Google Fonts не пустит. Сбор телеметрии в `postinstall` этих пакетов выключен в `pnpm-workspace.yaml`.

UI держит состояние вне дерева React — сторы с подпиской и `useSyncExternalStore`; разбор патчей уезжает с главного потока в веб-воркер (`packages/ui/src/diff/worker.ts`); списки виртуализованы (`@tanstack/react-virtual`); композер комментариев — ProseMirror.

## 2. Поток данных

Агент в харнесе ревьюера получает ключ PR вида `<host>-<pr>` и запускает `devflow-diff-explain up`. Команда идемпотентна: живой сервер этого PR находится по манифесту и переиспользуется, иначе поднимается демон — тот же CLI командой `devflow-diff-explain server`, которая грузит соседний модуль сервера, — переживающий выход CLI (`packages/cli/src/up.ts`). Ни pnpm, ни чекаута репозитория для этого не нужно. `up` печатает ссылку на UI и при холодном старте открывает браузер.

Ключ PR можно не называть: без него CLI определяет PR по каталогу запуска — arc-чекаут, текущая ветка, PR ветки (`packages/cli/src/pr-discovery.ts`). Ни один шаг этой цепочки не имеет права уронить команду: провал любого превращается в однострочную причину для человека.

Команды CLI и их роль:

| Команда | Что делает |
|---|---|
| `up` | поднимает сервер PR (или находит живой) и печатает ссылку на UI |
| `worker register` | объявляет сессию агента: харнес, модель, язык общения с ревьюером |
| `worker next` | ждёт задачу без срока; возвращает задачу с арендой, `done` или ошибку |
| `task complete` \| `progress` \| `fail` | сдаёт результат файлом, шлёт статусную строку, сообщает о провале |

Сервер — один процесс на PR. Он владеет всем состоянием этого PR и всеми записями в его базу.

**UI ↔ сервер: REST + SSE.** Ручки перечислены в `UI_ENDPOINTS` (`packages/protocol/src/ui.ts`), канал событий один — `GET /api/ui/events`. События (`state`, `review`, `progress`, `route`, `chat`) несут ревизию, а не данные: вкладка видит, что ревизия выросла, и перечитывает нужную ручку. Токен на этом канале приезжает параметром запроса, потому что `EventSource` не умеет заголовки; на всех остальных ручках — `Authorization: Bearer`.

**Сессия ↔ сервер: только pull.** Агент не принимает соединений и не имеет адреса. Он висит в долгом опросе `worker next`; сервер отдаёт задачу в аренду, агент делает работу и сдаёт результат отдельным вызовом.

Аренда — не изъятие из очереди: молча протухшая аренда возвращает задачу в очередь и тратит попытку. Новая сессия всегда права: регистрация со свежим `workerId` перехватывает слот, аренды вытесненного возвращаются в очередь. Подробности — `docs/protocol.md §2, §5, §7`.

**Типы задач** — `taskTypeSchema` в `packages/protocol/src/task.ts`:

- `echo` — проба петли, результат не разбирается;
- `route.skeleton` — выжимка PR, план остановок, порядок полного тура;
- `route.section` — заполнение остановок плана;
- `chat` — вопрос ревьюера с контекстом выделения; ответ markdown, схемы результата нет;
- `review.feedback` — раунд опубликованных комментариев локального ревью: агент правит код в каталоге проекта и отвечает в каждом треде.

Перегенерация после пуша — те же `route.*` с дополнительным контекстом, отдельного типа нет.

Задача самодостаточна: сессия могла умереть и переподключиться, поэтому весь нужный контекст лежит в ней, а память сессии — бонус, не контракт.

Промпт едет текстом (`instructions`), тяжёлый контекст — путями к материализованным сервером markdown-файлам (`contextFiles`), у структурных задач приложена JSON-схема результата (`resultSchemaFile`). То, что между задачами не меняется (дифф, файлы, методичка), лежит по стабильному пути в `payload/shared`: модель по пути видит, что этот файл в сессии уже читала. Результат сдаётся файлом, лимит — `RESULT_MAX_BYTES` (256 КБ).

Вопрос из чата проходит тем же путём: ручка складывает его в очередь задачей `chat` с контекстом выделения, ответ приходит через `task complete` и попадает в историю; из ответа ревьюер может сделать заметку у строки или черновик комментария.

**Генерация идёт в харнесе ревьюера, а не на сервере.** У сервера нет ни ключей моделей, ни клиента к ним: он готовит контекст, ставит задачу, принимает результат и валидирует его. Модель работает в той же сессии, где сидит ревьюер, на его правах доступа.

Наружу сервер ходит только в API хоста (Арканум или GitHub) и в трекер, когда ревьюер отправляет фидбек. Проверка, не вышла ли новая версия дистрибутива, идёт по тому же API Арканума и только уведомляет: Devflow Diff Explain ничего не скачивает и не ставит (`packages/server/src/update-check.ts`).

**Хост-адаптер** — единственная дверь к данным PR. Его выбирает сервер по префиксу ключа PR; всё, что знает о конкретном хосте, живёт за этой дверью (§5).

## 3. Хранилище `~/.sherpa`

Корень состояния — `~/.sherpa`; в тестах и дев-запусках его переопределяет переменная `SHERPA_DIR`. Пути собираются в одном месте с каждой стороны: `packages/server/src/paths.ts` и `packages/cli/src/paths.ts`.

```
~/.sherpa/
  servers/<prKey>.json     манифест discovery, 0600
  prs/<prKey>/
    sherpa.db              SQLite этого PR
    server.log             лог демона: пишет сервер, читает CLI, когда сервер не поднялся
    worker-id              идентичность сессии: пишет сервер при регистрации, читает CLI
    local-host.json        только у локальных ключей `local-*`: каталог проекта, ветка, база и поручение на исход ревью (`--verdicts`), 0600
    local-review.json      только у локальных ключей `local-*`: комментарии локального ревью, 0600
    local-iterations/      только у локальных ключей `local-*`: история итераций рабочего дерева — индекс и блобы новых сторон, 0700/0600
    payload/shared/        контекст, общий для задач: дифф, файлы, методичка
    payload/route/         payload генерации маршрута, чистится на каждую генерацию
    payload/chat/          payload вопросов чата, свой каталог на задачу
    payload/feedback/      только у локальных ключей `local-*`: payload раундов публикации, каталог на раунд
    blobs/                 кэш байтов картинок диффа
  settings.json            глобальные настройки UI, 0600
  update-check.json        кэш проверки версии, живёт 30 минут
```

Ключ PR валидируется схемой `prKeySchema` обеими сторонами, потому что подставляется в путь: без ограничения алфавита он увёл бы запись из `~/.sherpa`.

**Манифест** (`serverManifestSchema`) — `prKey`, порт, PID, токен, версии протокола и сервера, время создания. По нему CLI находит живой сервер, а UI — ничего: ссылку с токеном печатает CLI. Публикация атомарна: сервер готовит файл рядом и заводит по месту через `link`, единственную в POSIX связку «создай, если нет» (`packages/server/src/manifest.ts`). Занятое место означает, что сервер этого PR уже есть. Манифест мёртвого процесса сервер чистит при старте (CLI манифесты не трогает); живость проверяет не только по PID, но и запросом `/healthz` с токеном из манифеста — порт мог занять кто угодно.

**Права.** Каталоги внутри `~/.sherpa` — 0700, манифест и `settings.json` — 0600. Режимы сервер доводит явным `chmod` после создания: `mkdir` и `writeFile` применяют их с учётом umask, а каталоги могли существовать и раньше.

**База PR** — `sherpa.db`, WAL, схему доводит список миграций (`packages/server/src/migrations.ts`); имя миграции фиксировано навсегда, SQL применённой не переписываем. Вложенных транзакций у `node:sqlite` нет, поэтому все операции сервера идут через хелпер `transaction` с `BEGIN IMMEDIATE`, а доменные ошибки возвращаются значением, не исключением: исключение откатывает всё.

Перезапуск сервера переживают: очередь задач и их аренды, идентичность воркера, прогресс чтения (отметки файлов и остановок, диапазоны), снапшоты маршрута и состояние генерации, итерации и посчитанные интердиффы, история чата и заметки агента, буфер черновиков, привязка раундов локального ревью к их задачам, per-PR состояние UI, счётчик простоя. В памяти живёт только то, что дёшево пересоздать: подписки на хост, открытые SSE-каналы, кэш разобранных патчей во вкладке.

Настройки UI (`diffMode`, `shipMode`, раскладка композера, язык, тема, размер текста, состояние знакомства и уведомлений об обновлениях) лежат одним файлом на пользователя, а не в базе PR: сервер каждого PR слушает случайный порт, и `localStorage` браузера для нового порта каждый раз пуст. Истина всегда на диске — и чтение, и слияние патча берут свежее содержимое файла.

Тему и размер текста сервер подставляет в отдаваемый `index.html` (`packages/server/src/ui-document.ts`): первый кадр обязан прийти в сохранённой теме, а ответ `GET /api/ui/settings` — это уже второй кадр. Явная тема едет атрибутом `data-theme` на `<html>`, режим Auto — встроенным скриптом в `<head>`, который ставит атрибут по системной теме до подключения стилей. Дальше тему ведёт UI (`packages/ui/src/settings/document-settings.tsx`): в `data-theme` всегда резолвленное значение, про `auto` CSS не знает. До ответа `GET /api/ui/settings` UI атрибуты не переписывает — первый рендер идёт по таймауту и на медленной или упавшей ручке видит в сторе умолчания, а не выбор ревьюера.

## 4. Маршрут: оркестратор и валидатор

Маршрут строится в две фазы. `route.skeleton` даёт выжимку PR, план остановок с тирами и порядок полного тура. `route.section` заполняет остановки плана: абзац, связку к следующей, якоря в дифф, дайджест утверждений про тесты. Фазы состояния — `none / reading / filling / ready / failed` (`uiRoutePhaseSchema`).

**Снапшот** (`routeSnapshotSchema` в `packages/protocol/src/route.ts`) привязан к коммиту и итерации, для которых строился: `commit`, `baseCommit`, `diffId`. Происхождение записано в `provenance`: харнес, модель и язык генерации. Снапшот появляется с момента принятого скелета, дополняется по мере сдачи секций и становится неизменяемым в фазе `ready` — тогда же считается контент-хеш. Снапшотов у PR много, текущий один; прошлые остаются читаемыми.

**Валидатор** — чистые модули `packages/server/src/route/`: ни базы, ни сети, ни очереди. Сначала результат разбирает схема, потом идёт проверка семантики.

Приёмка fail-closed и синхронная — внутри транзакции `complete`. Отвергнутый результат не снимает аренду и не тратит попытку — модель правит его сама. У этой петли есть дно: `MAX_RESULT_REJECTIONS` (3) отказов подряд закрывают задачу ошибкой с последним сырым выводом.

Деградация в секциях двухуровневая. Мягкие правила режут отдельный элемент и оставляют ревьюеру пометку: якорь в несуществующий файл, якорь мимо изменённых строк, диапазон, уже занятый другой остановкой, ссылка на несуществующий тред. Жёсткие отвергают результат целиком: чужой или несуществующий плановый номер, `end < start`, остановка, у которой не выжил ни один якорь.

Скелету дифф не нужен — там семантика одна: `tourOrder` обязан быть перестановкой плановых номеров, иначе полный тур не построить. Идентификаторы остановок и синтетическое «Прочее» назначает сервер после валидации, модель их не выбирает.

Непокрытое собирается в синтетическую остановку **«Прочее»**: её добавляет сервер, модель о ней не знает, содержимое (непокрытые диапазоны) считает UI. UI её прячет, пока маршрут не достроен и пока в ней нет ни одной непокрытой строки (`otherStopVisible` в `packages/ui/src/route/other-stop.ts`); когда непокрыто больше 40 % изменённых строк (`PROMOTE_THRESHOLD` в `packages/ui/src/route/route-model.ts`), она поднимается наверх и UI предлагает перегенерировать маршрут.

**Автомат оркестратора работает на сверке.** `RouteOrchestrator.reconcile` не помнит событий: он читает состояние `RouteStore` рядом с состоянием очереди и решает, что делать дальше. Сверка идемпотентна, поэтому рестарт сервера посреди генерации, смерть агента и вытеснение сессии лечатся сами — отдельного кода для них нет.

Первую генерацию сервер ставит сам на прогреве (через 200 мс после старта, чтобы не задерживать дифф), если фаза `none`, агент подключён и открытых задач маршрута нет. Фаза `failed` лечится только кнопкой: иначе сервер бесконечно бился бы о ту же стену. Фаза `filling` без задач — это рестарт сервера, а не повод строить маршрут заново, поэтому починка прерванной генерации идёт до автопостановки.

**Порог «маленький PR»** — `isSmallPr` в `packages/server/src/route-orchestrator.ts`: сумма добавленных и удалённых строк по всем файлам не больше `smallPrMaxChangedLines` (по умолчанию 40, поле `RouteConfig`). Число файлов на порог не влияет: один файл на пятьсот строк маршрута требует. Маленький PR читается целиком — генерация не ставится, UI открывается на полном диффе с пометкой (`uiRouteState.smallPr`).

**Новая итерация.** Сервер сравнивает итерацию снапшота с активной итерацией хоста и отдаёт UI `uiRouteStale`: коммиты, сколько итераций появилось (force-push считается за одну) и какие остановки затронуты — по интердиффу между итерациями.

Перегенерацию запускает ревьюер кнопкой, автоматически она не стартует. Старый маршрут остаётся читаемым до приёмки нового скелета, подмена атомарна.

Задаче перегенерации в контекст едет прошлый маршрут и обсуждение, появившееся с тех пор (`packages/server/src/route-regeneration.ts`). При нехватке бюджета первыми режутся абзацы остановок с конца плана, таблица плана уходит последней, и урезание помечается в тексте явно.

**Перенос прогресса** сервер делает при приёмке нового снапшота, в той же транзакции: отметки остановок переезжают по карте строк интердиффа, итог уходит в `carried`. Остановки с неизменёнными диапазонами остаются отмеченными.

Классификацию остановки относительно прошлого снапшота сервер считает сам и детерминированно: `new` — все строки якорей затронуты или файл появился, `changed` — часть. Модель её не выбирает, только объясняет словами.

Без флага возможностей `iterations` у хоста ничего этого нет: срез между итерациями отклоняется, и UI показывает только «маршрут устарел».

## 5. `ReviewHost` и `HostCapabilities`

Интерфейс — `packages/protocol/src/review-host.ts`. Обязательные методы делятся на четыре группы:

- чтение PR: `getPr`, `listIterations`, `getDiff`;
- подписки: `watchIterations`, `getThreads`, `watchThreads`;
- запись: `saveDraft`, `updateDraft`, `deleteDraft`, `setThreadResolved`, `publishBatch`;
- линзы: `ownershipLens` (a.yaml, CODEOWNERS или весь дифф у локального ревью; `null` — у хоста нет понятия владения), `extraLenses`; имя источника зон для подписей UI — свойство `ownershipSource`.

Необязательные — `setFileViewed`, `getFileContent`, `getBlob`, `setCommentResolved`, `updateComment`, `deleteComment`; каждый привязан к своему флагу возможностей.

Подписки обещают полный снапшот один раз сразу и потом на каждое изменение. Транспорт — дело адаптера: общий знаменатель хостов — опрос, поэтому обещаем не реактивность, а сходимость.

`getDiff` без аргументов отдаёт активную итерацию, с парой итераций — срез между ними (что изменилось от одной к другой).

Возможности хоста объявляет `hostCapabilitiesSchema` (`packages/protocol/src/review.ts`): список режимов публикации и семь флагов.

| Поле | Что включает |
|---|---|
| `publishVerdicts` | режимы публикации, которые хост примет на этом PR: `comment` (черновики без вердикта), `ship`, `sticky_ship`, `request_changes`; состав, включая `comment`, решает хост. Панель публикации рисует ровно этот список и хосты не различает; вердикт вне списка хост отклоняет. Список считается на каждое чтение шапки: он зависит от PR, а не только от хоста |
| `fileViewedSync` | синхронизацию отметки «просмотрено» с хостом; без неё `file.viewed` всегда `null`, прогресс живёт только у нас |
| `fileContent` | «Expand context» — разворот файла за пределы патча |
| `commentIssues` | контрол «комментарий открывает issue / не требует ответа» |
| `commentResolve` | resolved на каждом комментарии с issue (`setCommentResolved`); `Thread.resolved` адаптер считает по правилу «есть issue и все закрыты», без флага `Comment.resolved` всегда `null` |
| `editPublished` | правку и удаление своих уже опубликованных комментариев (`updateComment`, `deleteComment`) |
| `iterations` | список прошлых итераций и срез между ними; без него доступно только «маршрут устарел» — ни переноса прогресса, ни классификации остановок |
| `blobs` | карточку-картинку в диффе; без неё бинарный файл остаётся строкой «двоичный файл не показан» |

Шапка PR несёт и личность того, кто её читает: `PrMeta.viewer` — ревьюер этой сессии (`null` — хост личность не знает). По нему UI отличает свои опубликованные комментарии от чужих, поэтому у хоста с `editPublished` он обязан быть заполнен.

**Инвариант: метод реализован тогда и только тогда, когда поднят соответствующий флаг.** Его стережёт общий контрактный набор `describeReviewHostContract` (`packages/server/src/hosts/review-host-contract.ts`), который гоняем одним и тем же списком тестов на всех реализациях. Он же проверяет формы ответов схемами протокола, обещания подписок, двухступенчатую модель черновиков и согласованность `file.viewed` с `fileViewedSync`.

Реализаций четыре: **Арканум** (`packages/server/src/hosts/arcanum/`), **GitHub** (`packages/server/src/hosts/github/`), **локальный чекаут** (`packages/server/src/hosts/local/`) и **фикстурный хост** (`packages/fixtures`) — детерминированные PR для дев-режима, галереи состояний и e2e. Локальный хост один на две системы контроля версий: вся работа с VCS спрятана за интерфейсом `LocalVcs` (`vcs.ts`), а бэкендов у него два — `arc-vcs.ts` и `git-vcs.ts`.

Арканум поднимает все семь флагов; `editPublished` снимает ответ без заголовка с логином владельца токена (тогда `viewer` пуст и правки своего опубликованного нет). Режимы публикации — `comment`, `ship`, `request_changes` и `sticky_ship`, пока стики-шип не выключили настройки PR; `comment` публикует черновики и вердикта не ставит.

**Адаптер Арканума ходит в два источника.** По HTTP из Арканума приезжают метаданные: мета PR, список итераций, changelist итерации и среза, треды и черновики, публикация и вердикты, отметки «просмотрено», правила ревью `a.yaml` и линзы. Сам контент — текст диффа, текст среза, содержимое сторон файла и байты картинок — читается локальным `arc` (`packages/server/src/hosts/arcanum/arc-cli.ts`): `arc diff --git <base> <merge> -- <пути…>` по путям changelist и `arc show <blob>` по хэшам блобов оттуда же. Тяжёлые ручки Арканума (`…/patch`, `text-diff`, `/repos/content/file`) из адаптера убраны насовсем — они не держали нагрузку.

Поэтому ревью Арканума требует смонтированного чекаута того репозитория, в котором живёт PR. Адаптер обслуживает оба тенанта Арканума — Аркадию и Cloudia; тенант PR он узнаёт из меты (`vcs.arc_repo_name`) одним мемоизированным запросом и дальше выбирает им чекаут, репозиторий в ручках правил ревью a.yaml и веб-ссылки (blame ведёт в `a.yandex-team.ru/<тенант>/…`, ссылка на файл — в `url` PR из той же меты). Линза PCI DSS есть только у Аркадии: у остальных тенантов скоупа аудита нет, и ручка не дёргается вовсе.

Маунт адаптер находит сам, без флагов и переменных окружения: сначала тот, внутри которого запущен сервер (`arc root` из каталога запуска), иначе первый живой из `arc mount --list --json`. Шаги независимы: список маунтов спрашивается из домашнего каталога, а не из каталога запуска, который мог уехать вместе со снятым ворктри. Годится только чекаут нужного репозитория — у Аркадии и Cloudia разные object-store: запись списка отсеивается по полю `tenant`, а в прежнем формате `arc`, где поля нет, репозиторий кандидата называет `arc info --json`. Внутри репозитория объекты `arc` адресуются содержимым и лежат в общем object-store, так что подходит любой его чекаут — ветка и рабочее дерево значения не имеют. Ни `arc`, ни живого маунта нужного репозитория нет — ручки диффа и содержимого отвечают `host_unavailable`, называя репозиторий и команду монтирования; фолбэка в Арканум за контентом нет намеренно.

**Адаптер GitHub** ревьюит PR на github.com по ключу `github-<владелец>--<репозиторий>--<номер>` (разделитель — удвоенный дефис: у владельца его не бывает, у репозитория бывает). Основной API — GraphQL: мета, треды, ревью и вердикты, отметки просмотра, текст файлов, все записи. REST остаётся ровно на трёх вещах, которых в GraphQL нет: текст патча (`…/pulls/{n}/files`), merge-base (`…/compare/{base}...{head}`) и байты картинок (`…/contents/{path}`). Токен — цепочка `gh`: `$GITHUB_TOKEN` → `$GH_TOKEN` → `gh auth token`; чекаут репозитория не нужен.

Итерация у GitHub одна: понятия диффсета нет, ревьюется голова ветки против merge-base, поэтому `iterations` снят и срез отклоняется. Из семи флагов подняты `fileViewedSync`, `fileContent`, `blobs` и `editPublished`; `commentIssues` снят — такого понятия у GitHub нет, а `commentResolve` снят потому, что issue у GitHub нет: закрывается тред целиком. Режимы публикации на чужом PR — `comment`, `ship` и `request_changes` (стики-шипа у GitHub нет), на своём (логин автора PR совпадает с владельцем токена без учёта регистра) — только `comment`: автору GitHub запрещает и апрув, и запрос правок.

Владение считает CODEOWNERS базовой ветки PR — первый найденный из `.github/CODEOWNERS`, `CODEOWNERS`, `docs/CODEOWNERS`, одним запросом с тремя алиасами. Владельцев файла называет **последнее** совпавшее правило (в отличие от a.yaml, где складываются все покрывающие), оно же задаёт границу зоны; правило без владельцев снимает владение, и такой файл остаётся вне зон. Команды-владельцы (`@org/team`) разворачиваются отдельным запросом `organization.teams(userLogins:)` — он требует скоупа `read:org`, и его отказ деградация, а не ошибка: линза строится по логинам, а `note` говорит, что владение по командам не посчитано.

Черновики живут в pending-ревью GitHub: комментарий к строке заводится прямо в нём, а черновик уровня PR — абзацем тела ревью, потому что другого места для неопубликованного текста у GitHub нет. Абзацы помечены строкой-маркером `<!-- devflow-diff-explain:draft <n> -->` (на GitHub она не рендерится): маркер даёт абзацу постоянный id, который переживает и правку соседей, и публикацию. Само тело пустым не остаётся никогда: ревью, заведённое без тела, GitHub навсегда закрывает для правки, поэтому pending-ревью создаётся с заглушкой `<!-- devflow-diff-explain:body -->`, и она же пишется вместо пустой строки, когда удалён последний абзац. Публикация — один `submitPullRequestReview`, которому итоговое тело едет параметром (заглушка в опубликованное ревью не уходит): частичного успеха у GitHub не бывает, сабмит либо уносит все черновики с вердиктом, либо не уносит ничего. `comment` уходит событием `COMMENT`, а без черновиков ничего не делает — pending-ревью с одной заглушкой так и остаётся. Ключей идемпотентности GitHub не понимает, поэтому карту «ключ повтора → комментарий» держит сам адаптер в `~/.sherpa/prs/<key>/github-drafts.json`.

Локальный хост ревьюит рабочее дерево каталога проекта в arc- или git-чекауте относительно базового коммита: закоммиченное, staged, unstaged и неотслеживаемое одним диффом. Активная итерация — текущее состояние дерева, новая появляется, когда дифф действительно изменился, а прошлые адаптер помнит сам: их состав и содержимое новых сторон лежат в `~/.sherpa/prs/<key>/local-iterations/`, и по ним же считается срез между двумя итерациями. Из семи флагов подняты `fileContent`, `blobs`, `iterations` и `editPublished` (свой комментарий правится и удаляется прямо в локальном хранилище); без `iterations` правка одного файла снимала бы отметки просмотра со всего диффа. Issue локально нет, поэтому нет и резолва по комментарию: закрывается тред целиком. Зона ревьюера — весь дифф, источник зон (`ownershipSource`) — `arc diff` или `git diff` по VCS каталога. Головного коммита у дерева нет: `headCommit` итерации — тот же отпечаток диффа, что и `diffId`. Комментарии лежат рядом со стейтом ревью: удалённого хоста у них нет. По умолчанию режим публикации один — `comment`: вердикт здесь применять некому, замечания пишутся для агента. С `devflow-diff-explain up --local … --verdicts '<поручение>'` режимы как в PR — `request_changes` и `ship`, без `comment`: вердикт ждёт агент, которому пользователь поручил действие на одобрение или на запрос правок, а само поручение его словами — значение флага; режим вне списка хост отклоняет. Публикация снимает с черновиков признак черновика и открывает раунд: `comment` — если опубликован хоть один комментарий, вердикт — и без комментариев, его сессия обязана узнать. Раунд оркестратор (`packages/server/src/feedback-orchestrator.ts`) превращает в задачу `review.feedback`: на `comment` и `request_changes` агент правит код по каждому замечанию, отвечает в тредах бот-комментариями, и его правки заводят новую итерацию — маршрут устаревает, ревьюер читает заново. На `ship` изменения одобрены: агент отвечает в тредах, если комментарии есть, и выполняет поручение. Текст задачи на `ship` и `request_changes` печатает поручение дословно, в кавычках; у `request_changes` — после просьбы править код по замечаниям. Поручение берётся у хоста в момент сборки задачи, в раунде оно не хранится. Если к этому моменту режим снят, поручения нет, и на `ship` остаётся общий текст «если пользователь просил что-то сделать на одобрение — сделай».

Выбор по префиксу ключа PR в `packages/server/src/hosts/select.ts`: `arcanum-<число>` — живой Арканум, `github-<владелец>--<репозиторий>--<номер>` — PR на github.com, `local-arc-<каталог>-<хеш>` и `local-git-<каталог>-<хеш>` — локальный чекаут (префикс называет и бэкенд VCS), `fixture-<имя>` — фикстура, что угодно другое — хоста нет, и ревью-ручки отвечают `no_review_host`. Локальному хосту нужен ещё каталог проекта: его называет `devflow-diff-explain up --local <path>` (аргумент сервера `--repo`), и он же сохраняется в `~/.sherpa/prs/<key>/local-host.json` — перезапуск демона обходится без флага. Прогресс чтения при этом остаётся доступен: он локальный и хоста не требует.

**Хост-специфика не выходит за адаптер.** Идентификаторы хоста непрозрачны (`hostIdSchema`): у Арканума это знаковые числа и base64-протобуфы, контракт не обещает ничего, кроме равенства. Стики-шип — вердикт, а не механика. Немногое, что адаптеру всё же нужно наружу (подписка на смену статуса ревью у Арканума, принудительный опрос рабочего дерева и раунды публикации у локального хоста, дев-«пуш» и переключатель отказа записи у фикстуры), лежит в `SelectedHost` и дальше точки регистрации соответствующих маршрутов не уходит: общий код сервера о фикстурах не знает.

## 6. Нефункциональные требования

**Производительность.** Дифф оказывается на экране раньше маршрута: старт сервера не ждёт `getDiff`, прогрев уезжает в отложенный таймер, который не держит процесс живым.

Дерево файлов и список карточек виртуализованы, разбор патчей идёт в веб-воркере. Файл, у которого больше 2000 изменённых строк, рендерится свёрнутым (`COLLAPSE_THRESHOLD` в `packages/ui/src/diff-view/file-card.tsx`). Карточки, уехавшие далеко от вьюпорта, UI снимает с DOM и возвращает по гистерезису двух границ: с одной границей они мигали бы на каждом кадре, когда край остановки стоит ровно на ней.

Бюджет времени кадра — средний ≤ 16,7 мс, p95 ≤ 33 мс — меряется на фикстуре `fixture-huge` (100 файлов, около 25 тысяч изменённых строк) отдельным прогоном `packages/e2e/src/performance.spec.ts`.

**Безопасность.** По умолчанию всё живёт на localhost. `SHERPA_LISTEN_HOST=::` открывает сервер по IPv6 и IPv4; ссылка UI тогда использует имя виртуалки. Bearer-токен обязателен на каждой API-ручке, включая UI; послабление одно — SSE, где токен приезжает параметром запроса, потому что `EventSource` не умеет заголовки. Прямой HTTP-доступ не шифруется.

Токены сервер сравнивает по хешам за постоянное время (`packages/server/src/auth.ts`): сравнение самих строк требует равной длины и выдало бы длину настоящего токена. Токен в ссылке на UI стоит во фрагменте — на сервер он не уходит, но переживает перезагрузку страницы.

Манифест и настройки — 0600, каталоги состояния — 0700. Наружу уходят только запросы к API хоста и к трекеру, когда ревьюер сам отправляет фидбек.

**Надёжность.** Сервер переживает смерть агента: аренды вытесненной или молчащей сессии возвращаются в очередь, а сверка чинит фазу генерации. UI переживает смерть сервера — вкладка показывает баннер и переподключается.

Черновики не теряются. Запись появляется в таблице буфера на каждое сохранение и исчезает, только когда хост её принял; провал шага «сервер → хост» оставляет строку в буфере, и её довозят повтором по таймеру (10 с → 30 с → минута), кнопкой и при следующем старте сервера. Повтор идёт с ключом идемпотентности, чтобы не завести второй комментарий. Буфер — сохранённое состояние композера, а не фантомный комментарий: в снапшот тредов его записи не подмешиваются.

Результат сверх лимита завершает задачу понятной ошибкой, а не молча; ошибка задачи видна в UI.

**Самоостановка по простою.** Сервер PR — фоновый демон, команды остановки в контракте нет, поэтому он гасит себя сам: 15 минут без открытых соединений и без запросов (`DEFAULT_IDLE_SECONDS`, `packages/server/src/idle.ts`).

Занятость сервер считает по одному входу в роутер. Внутренние таймеры — служебные пинги SSE, таймер смерти воркера — активностью не считаются, иначе сервер не умрёт никогда. Состояние переживает остановку в базе, следующий `up` поднимает сервер заново.

Отдельно от простоя — уход ревьюера: сигнал завершения петли уходит агенту, когда последнее UI-соединение закрыто дольше `UI_GONE_GRACE_SECONDS` (60 с). Перезагрузка страницы, переход между вкладками, сон ноутбука и моргнувшая сеть рвут SSE на секунды, и это не уход.

**Телеметрии нет.** Devflow Diff Explain не собирает и никуда не отправляет события: ни продуктовых, ни технических. Единственный канал обратной связи — тикет, который ревьюер заводит явным действием.

## 7. Инварианты

**7.1. «Просмотренная строка» выводится только из ручных отметок.** Слежения за вьюпортом нет. Просмотренные диапазоны файла — объединение диапазонов остановок, которые ревьюер отметил вручную целиком или по одной карточке файла, плюс файлы, отмеченные вручную в полном диффе; из них выводятся три состояния файла (`read` — покрыты все изменённые строки, `partial` — часть, `unread` — ничего). `IntersectionObserver` в UI есть, но только для решений о рендере: какие карточки заказать в разбор и какие держать в DOM. Прогресса он не пишет. Автоотметка остановки существует, но её вход — те же ручные отметки файлов: остановка отмечается, когда её диапазоны уже покрыты ими.

**7.2. Фильтр прячет остановки без подходящих файлов, номера остаются плановыми.** Остановка, у которой под текущим фильтром не осталось ни одного файла, уходит из вида; карточка, удержанная на экране, остаётся видимой. Номер остановки (`planIndex`) фиксируется скелетом и заполнением не меняется: фильтры и подъём «Прочего» переупорядочивают рендер, но не нумерацию.

**7.3. Сочетания клавиш объявляются один раз.** Единый реестр — `packages/ui/src/shortcuts/registry.ts`; из него строятся и командная палитра, и читшит. Второго места, где живут сочетания, в UI нет. Слушатель `keydown` тоже один: он решает, чья это клавиша, разводя команды по областям (`global`, `route`, `full-diff`, `overview`), и держит лестницу Esc — слои оверлеев закрываются по старшинству, по одному на нажатие. Клавиша сверяется по набранному символу, а когда он не латинская буква или цифра — ещё и по физической клавише (`event.code`), чтобы команды работали в русской раскладке.

**7.4. Глубина веток ответов ограничена отступом.** Отступ растёт до четвёртого уровня, дальше не увеличивается; глубже ответ подписывается автором того, кому отвечает (`packages/ui/src/threads/model.ts`).

**7.5. Сервер — на PR, хранилище — SQLite, payload задач — файлы.** Один процесс-владелец на PR, все записи в базу идут через него, WAL. Тяжёлый контекст задачи сервер материализует markdown-файлами, схему прикладывает только на результат. Лимит результата — `RESULT_MAX_BYTES` (256 КБ), больше — задача завершается ошибкой с понятным текстом. Контекстные файлы режутся по бюджету с явной пометкой об урезании (`packages/server/src/payload-budget.ts`), чтобы модель не считала обрезанный контекст полным.

**7.6. Порог маленького PR — 40 изменённых строк.** Считается сумма добавленных и удалённых строк по всем файлам; число файлов не влияет. Порог — поле конфигурации маршрута, не константа в коде вызова.

**7.7. Новая сессия всегда права.** `register` со свежим `workerId` перехватывает слот воркера даже у живой сессии; аренды вытесненной сессии сразу возвращаются в очередь. Сам `register` конфликта не отдаёт никогда — вытесненная сессия узнаёт о потере слота из своего следующего вызова, а её висящий долгий опрос `next` возвращается с `worker_conflict` в ту же секунду, не досиживая окно ожидания (`packages/server/src/worker-routes.ts`, `packages/server/src/worker-registry.ts`). Регистрация с тем же `workerId` — идемпотентное продление; вызов без `register` занимает свободный слот, но живого владельца не вытесняет. Сюда же относятся два правила отображения: «Прочее» поднимается наверх, когда непокрыто больше 40 % изменённых строк (§4), и сгенерированные файлы стартуют свёрнутыми как прочитанные, пока ревьюер не развернёт их вручную.
