# Тестирование

## 1. Проверки

Перед любым коммитом должно быть зелено:

```
pnpm -r typecheck && pnpm -r lint && pnpm -r test
```

- `typecheck` — `tsc --noEmit` по каждому пакету (у `skill` типизировать нечего, скрипт печатает это и выходит).
- `lint` — eslint по каждому пакету.
- `test` — `vitest run` в шести пакетах: `protocol`, `fixtures`, `cli`, `server`, `ui`, `skill`.

E2E в обязательные проверки не входит: у `packages/e2e` нет скрипта `test`, только `e2e`. Playwright гоняем отдельно — перед релизом и после правок в `packages/e2e`, сервере и тех потоках UI, которые e2e покрывают. Перф-спека входит в обычный e2e (§5).

Живой Арканум и живая модель в тестах запрещены: хост ходит через записанные ответы, генерация — через сырые выводы из фикстур.

## 2. Юнит-тесты по пакетам

Общего конфига vitest нет, каждый пакет запускается своим. У `protocol` и `fixtures` конфига нет вовсе — всё по умолчанию (окружение `node`, форки, изоляция). Setup-файлов нет ни в одном пакете.

**`protocol`** — один файл на все схемы: версия и совместимость рукопожатия, задача и аренда, `complete`, манифест discovery, доменные типы ревью (PR, дифф, треды, линзы), маршрут, чат и заметки, итерации и снапшоты, настройки/онбординг/обновление, генерация JSON-схем. Проверяем обе стороны: валидная форма проходит, кривая отбивается — лимиты (`RESULT_MAX_BYTES` считается в байтах, не в символах), нулевые попытки, неизвестные типы задач, битый узел в глубине дерева тредов валит весь тред.

**`server`** — самый большой набор. `vitest.config.ts` задаёт только `globalSetup: ['./src/bundle.global-setup.ts']`: файлы тестов идут параллельными форками, а esbuild перезаписывает бандл неатомарно, поэтому сборка вынесена в один прогон на весь набор. Глобальный сетап собирает UI (пропускает, если `packages/ui/dist/index.html` уже есть) и сервер-бандл.

Роуты проверяем только на живом HTTP — вызовов обработчиков напрямую нет ни одного. Три формы: полное приложение через `startServer` (реальный `http.createServer` на `listen(0, '127.0.0.1')`, своя БД, манифест, фикстурный хост); голый HTTP-слушатель с руками собранными роутами и заглушёнными оркестраторами; отдельный процесс ОС — `bundle.test.ts` поднимает собранный модуль `dist/devflow-diff-explain-server.mjs` через обёртку из двух строк (`import()` и вызов `runServer`), вычитывает порт и токен из манифеста и ходит обычным `fetch`; там же проверяется, что голый импорт модуля ничего не запускает. Хелперы запросов и временных каталогов — `packages/server/src/test-support.ts`.

Хранилище — встроенный `node:sqlite`, схему набирает список миграций (`packages/server/src/migrations.ts`), в который только дописывают, версия равна числу применённых. `db.test.ts` проверяет: создание с нуля и режим WAL (подтверждается отдельным коннектом), идемпотентность повторного открытия, апгрейд **с любого префикса списка** (цикл по всем промежуточным состояниям), адресные переносы данных, атомарность падения (сломанная миграция не оставляет полуготовой таблицы), гигиену списка (уникальность имён, формат `NNN-имя`, сплошная нумерация).

Валидатор маршрута прикрыт с двух сторон: golden-набор (§3) и негативный корпус `packages/server/src/route/corpus.test.ts` — таблица рукописных кривых результатов со сверкой текста ошибок дословно. Каждый случай «модель вернула странное» добавляет запись в корпус.

**`cli`** — конфиг тоже только с глобальным сетапом сборки бандла. Юниты покрывают разбор аргументов, проверку версии Node, открытие браузера, формат текста задачи, таймаут `next`, discovery PR по записанным выводам `arc`, поиск и загрузку модуля сервера, отсутствие внешних импортов и серверного кода в собранном бандле. `up.test.ts` спавнит демоном настоящий собранный CLI, подменяя только модуль сервера.

`cli.integration.test.ts` — команды вызываются функциями, но сервер настоящий: `up` (находит живой сервер, не открывает вкладку повторно, отсутствие модуля сервера рядом даёт «неполный дистрибутив»), `server` (аргументы уходят модулю как есть, модуль без `runServer` — «неполный дистрибутив»), `worker register` (файл состояния и его права, `--lang`, реконнект, вытеснение сессии), `task complete/progress/fail` (лимит текста, чужой номер задачи, чужой токен, мёртвый манифест).

`protocol.scenarios.test.ts` — протокол C1↔C2 против живого сервера, где воркера играет собранный бандл: `src/fake-worker.ts` запускает каждую команду отдельным процессом node, так что памяти между вызовами нет — ровно как у сессии-агента. Часы сервера подменены, поэтому протухание аренды наступает мгновенно. Сценарии: **умер молча** (аренда протухла, новая сессия получает ту же задачу второй попыткой), **вернул мусор** (`complete` отбит валидатором, задача остаётся арендованной, вторая попытка принимается), **повторил complete** (второй вызов — no-op, первый результат не перезаписан), **превысил lease** (сдача отбита, задача вернулась в очередь без владельца, работа не потеряна), отмена во время аренды, реконнект с перехватом слота, исчерпание попыток.

**`ui`** — отдельного конфига нет, блок `test` живёт в `vite.config.ts` и поднимает таймауты до 20 с. Окружение выбираем пофайлово докблоком `// @vitest-environment jsdom`; остальные файлы идут в `node`. Testing-library в проекте нет: DOM-тесты монтируют компонент вручную через `createRoot` + `act`, чистые рендерят в строку через `renderToStaticMarkup`. Снапшот-тестов нет ни одного — все ожидания записаны явно.

Темы: разбор диффа и подсветка, отрисовка строк и карточек файлов, треды и заметки, модель маршрута (покрытие пересчитывается из якорей и диффа, а не берётся из снапшота), прогресс чтения, палитра и горячие клавиши, i18n, сторы и разбор адреса, интеграция уровня `App` в jsdom против заглушённого транспорта.

Отдельно стоят три гвардии:

- `src/styles/tokens.test.ts` — таблица токенов из `docs/design/README.md` перенесена в литерал; тест читает `tokens.css`, вынимает объявления `--*` из `:root` и требует совпадения множества имён ровно, значений — после нормализации записи цвета. Лишний и пропавший токен валят одинаково.
- `src/icons/icon.test.tsx` — вырезает скрытый блок спрайта из `docs/design/Sherpa Additions.dc.html` и требует побайтового совпадения с нашей копией `sprite.svg`, плюс сверяет список идентификаторов символов и разметку компонента `Icon`.
- `src/i18n/no-cyrillic.test.ts` и `src/styles/component-styles.test.ts` — кириллица только в словаре и комментариях; цветовых литералов вне `tokens.css` нет, каждая `var(--x)` где-то объявлена.

**`fixtures`** — тесты не «примеры», а инварианты данных: детерминированность сборки, сходимость счётчиков ханков и номеров строк, восстановление полного текста файла из патча, совпадение срезов между итерациями с патчами самих итераций. Маршрутные фикстуры сверяются с диффом: покрытие пересчитывается из добавленных и удалённых строк и сравнивается с числами хендоффа.

**`skill`** — `vitest.config.mjs` задаёт `fileParallelism: false`, оба набора пересобирают `dist/`. `build.test.mjs` проверяет состав дистрибутива (`SKILL.md`, `bin/` с исполняемой командой и неисполняемым модулем сервера, `version.json`), побайтовое равенство `SKILL.md` исходному, содержимое `version.json`, запуск собранного CLI голым node и то, что сервер и UI в бандл CLI не протекли (CLI меньше сервера и не содержит `node:sqlite`). Сквозные проверки собранного `dist/` в копии во временном каталоге: холодный `up` поднимает сервер, тёплый переиспользует тот же; `worker next` не грузит модуль сервера, а `server` грузит. Там же — тест фраз-маркеров: из `SKILL.md` вынимаются все строки в кавычках, среди них обязана быть `stop the loop`, и каждая такая фраза плюс `DONE` обязана дословно встречаться в собранных бандлах. Разъедься формулировки — петля в харнесе молча перестанет узнавать ситуации. `release.test.mjs` гоняет `scripts/release.mjs` во временный каталог: раскладка файлов, исполняемый бит только у `bin/devflow-diff-explain.mjs`, печать готовых команд публикации (публикует человек), повторный запуск убирает протухшее, `builtFrom` совпадает с состоянием рабочего дерева, `releasedAt` и `whatsNew` дописываются в `version.json` и не попадают в `dist/`.

## 3. Контракт-сьют `ReviewHost`

`packages/server/src/hosts/review-host-contract.ts` — не тест, а функция `describeReviewHostContract(name, makeHost, { writes?, advance?, viewer?, skip?, slow? })`. Её вызывают все четыре реализации: `FixtureHost` (цикл по всем фикстурам), `ArcanumHost` на моках транспорта, `GithubHost` на записанном API GitHub и `LocalHost` — на фейковом `arc` с временным каталогом и на живом `git` во временном репозитории. Один набор проверок, четыре реализации — расхождение адаптеров ловится там же, где заводится (`docs/architecture.md §5`).

git-бэкенд локального хоста (`git-vcs.test.ts`, `local-git-host*.test.ts`) гоняется на настоящем `git`: репозиторий заводится во временном каталоге системы (никогда внутри чекаута arc) в изолированном окружении, а сам бэкенд зовётся как в продакшене — с конфигом машины; только имя автора задано в конфиге временного репозитория, чтобы логин в тестах не зависел от машины. Нет `git` на машине — наборы пропускаются целиком. Запуск процесса стоит около ста миллисекунд, поэтому потолки времени у этих наборов свои.

Что проверяется:

- `getPr` и `getDiff` валидны по схемам, идентификаторы файлов уникальны.
- **Метод ⇔ флаг возможности.** По каждому флагу `HostCapabilities` (`fileViewedSync`, `fileContent`, `blobs`, `iterations`, `commentIssues`, `commentResolve`, `editPublished`) проверка двусторонняя: флаг снят — метода на хосте быть не должно, и данные обязаны это отражать (отметка просмотра `null`, изображение `null`, ровно одна итерация, срез отклоняется); флаг стоит — метод обязан существовать. Объявить возможность и не дать метод так же нельзя, как дать метод молча.
- Содержательные следствия: `getFileContent` на бинарнике даёт `null`, а на текстовом файле контекстные строки патча лежат в тексте ровно на своих номерах (иначе раскрытие контекста дорисует не оттуда); несуществующий блоб — `null`, длина байтов равна заявленному размеру, слишком тяжёлая сторона изображения — `null`.
- Итерации: ровно одна активная, ни одной исчезнувшей (это ставит сервер, не хост), время не убывает; срез с неизвестной итерацией отклоняется, а не отдаёт пустой дифф; после «пуша» пути среза лежат в объединении двух итераций.
- Подписки: начальный снапшот приходит сразу, `getThreads` ему равен, после каждой записи приходит **новый** снапшот (рост числа доставок проверяется отдельно — хост, отдавший живую ссылку на свой массив, обещание не выполняет), отписка поток останавливает.
- Запись (если хост её умеет): цикл черновика (вместе с issue-статусом у ответа), идемпотентность сохранения по ключу, ответ в тред, разрешение треда и отдельного issue-комментария, правка и удаление опубликованного, публикация пакетом (черновиков не остаётся), отметка просмотра видна в следующем `getDiff`.
- Режимы публикации: `publishVerdicts` содержит `comment` и без повторов; каждый вердикт вне списка хост отклоняет, и черновик после отказа остаётся черновиком; `comment` без черновиков отвечает `{[], [], true}` и снапшот тредов не меняет; каждый вердикт из списка, кроме `comment`, публикует черновик на свежем хосте с `verdictApplied: true`.
- Резолв по комментарию: `Comment.resolved === null` ровно у хостов без `commentResolve`, а у остальных `Thread.resolved` каждого треда равен правилу «есть issue и все закрыты», посчитанному по его комментариям.

`GithubHost` гоняется дважды — на чужом PR и на своём (автор PR — владелец токена, из режимов остаётся `comment`) — на таком же моке `fetch`: `/graphql` разбирается по имени операции и переменным, REST — по трём маршрутам (файлы, `compare`, байты содержимого), мутации меняют дальнейшие ответы, «пуш» уводит голову ветки на новый коммит. Неизвестная операция — ошибка теста: адаптер не должен ходить туда, куда мок не смотрел.

`ArcanumHost` собираем с подменённым `fetch`: мок поверх записанных ответов Арканума. Мок с состоянием — записи меняют комментарии и отметки, время обновления двигается, иначе поллинг тредов ничего бы не заметил и набор с записью проверял бы статические файлы. Мок умеет отдавать ошибку на заданной ручке (так проверяется деградация линз), подменять тело между тиками поллинга и считать запросы (так проверяется кэш). Мок собирается под тенант — Аркадию или Cloudia: во втором случае мета PR называет репозиторий `cloudia`, ручки правил ревью обязаны идти в него, а `pci-dss` не обслуживается; контракт-сьют гоняется на обоих. Неизвестный запрос — ошибка теста. Отдельно проверяем, что токен не утекает в тексты ошибок.

**Golden-тесты** есть у валидатора маршрута, а не у правил ревью: `packages/server/src/route/golden.test.ts` берёт из фикстур сырые выводы модели (скелет и результаты секций — ровно то, что вернул бы агент) и ожидаемый готовый снапшот маршрута, прогоняет сырой текст через боевой валидатор и сверяет результат дословно. Покрыты: план из скелета вместе с синтетической остановкой «Прочее», совпадение результата при разбиении секций на пакеты, дайджест остановки с отбросом неподтверждённых утверждений, разрешение якорей в файлы активной итерации, второй проход после пуша, англоязычная генерация. Режима перегенерации нет — golden правим руками, а честность самих фикстур держит `packages/fixtures/src/route.test.ts`.

Правила ревью Арканума покрыты обычными юнитами: критерий призыва (кто и как считается вызванным ревьюером, поведение при неполном ответе) и диалект глобов в `subpaths` (`**` против `*`, классы символов, группы, экранирование, «побеждает последнее совпадение», ошибка разбора как ошибка, а не молчаливое несовпадение).

## 4. E2E

`packages/e2e` на Playwright, запуск `pnpm --filter @sherpa/e2e e2e`. Нужен Chromium:

```
pnpm --filter @sherpa/e2e exec playwright install chromium
```

Из внутреннего контура зеркало задаётся переменной окружения:

```
PLAYWRIGHT_DOWNLOAD_HOST=https://s3.mds.yandex.net/playwright-browsers \
  pnpm --filter @sherpa/e2e exec playwright install chromium
```

`global-setup.ts` один раз на прогон собирает то, что e2e гоняет как прод: статику UI и бандл CLI.

Каждый тест поднимает свой сервер на `FixtureHost` с отдельным временным `--sherpa-dir` и отдельным рабочим каталогом; оба удаляются после теста. Адрес и bearer-токен тест вычитывает из вывода сервера, прямые обращения к ручкам идут тем же токеном, что и UI. Сессию-агента играет `FakeWorker` поверх собранного бандла CLI — те же шелл-команды, что выполняет модель в харнесе; петлю пишет сам тест, потому что `worker next` долго ждёт задачу и её берут только тогда, когда сервер её заведомо поставил.

Дев-ручки объявлены в протоколе и регистрируются только у фикстурного хоста — у реального PR этих маршрутов не существует вовсе:

| Ручка | Зачем |
|---|---|
| `POST /api/dev/fixture/advance-iteration` | «автор запушил»: следующая объявленная итерация становится активной, вкладка узнаёт об этом по SSE |
| `POST /api/dev/fixture/fail-draft-writes` | хост отказывает на записи черновика — проверка буфера |

## 5. Перф-бюджеты

`packages/e2e/src/performance.spec.ts` идёт в общем прогоне e2e; отдельно:

```
pnpm --filter @sherpa/e2e e2e src/performance.spec.ts
```

Спека долгая (около полутора минут), внутренний таймаут huge-тестов поднят до 600 с.

Фикстура `huge` — 100 файлов и 25 274 изменённых строки. Под замер попадает не весь PR: 24 карточки свёрнуты по причине (просмотрено или машинный файл) и разбор не заказывают, поэтому до воркера и до отрисовки доходят 76 файлов и 21 260 строк. Числа зафиксированы константами в `@sherpa/fixtures` и проверяются самим тестом, так что цифры прогона читаются как нагрузка именно этого размера.

Что меряется:

- время до первого кадра диффа;
- разбор патчей в воркере: сумма, среднее, p95, максимум, число разобранных файлов (попадания в кэш не считаются);
- фреймтайм холодной и тёплой прокрутки, двумя рядами сразу — работа кадра (замер вокруг присвоения позиции с принудительным пересчётом раскладки) и интервал между соседними кадрами;
- число узлов DOM;
- размер кучи, если сборка Chromium его отдаёт.

Всё печатается строками `PERF …` и дублируется аннотациями отчёта.

Бюджет — среднее ≤ 16,7 мс, p95 ≤ 33 мс (`docs/architecture.md §6`). Он включён и падает прогон:

- на `large` (64 файла) — только по работе кадра, интервал между кадрами не проверяется;
- на `huge` — обе метрики, на холодном и тёплом проходе, в обоих huge-тестах; плюс потолок числа узлов DOM для маршрута.

Выключатель `HUGE_BUDGET_ENFORCED` в шапке спеки сейчас стоит в `true`. Он оставлен как одна точка правки на случай, когда бюджет надо временно снять; это не признак того, что бюджет только записывается.

## 6. Галерея состояний

`packages/ui/gallery.html` и `packages/ui/src/dev/gallery/` — детерминированный рендер состояний экрана на фикстурах из `@sherpa/fixtures`: ни сервера, ни токена, только статические свойства. Запуск:

```
pnpm --filter @sherpa/ui dev
```

и адрес `/gallery.html`. Слева — состояния, сгруппированные по подсистемам, справа — выбранное. Состояние, язык, тема и размер текста живут в адресной строке (`#state=…&locale=en&theme=auto|dark|light&textsize=m|l`; тема по умолчанию тёмная, чтобы карточки не зависели от темы системы), ссылку на конкретное состояние можно переслать. Смена состояния или языка перемонтирует рендер, так что начальные свойства применяются заново. В прод-сборку галерея не идёт: собирается только `index.html`.

Галерея — приёмка внешнего вида: она открывается рядом с прототипом `docs/design/Sherpa.dc.html` в одинаковом вьюпорте, и расхождения правятся до совпадения. Новое состояние или компонент — новая карточка в галерее.

Каждая нарезка состояний прикрыта тестом `*-states.test.tsx`. Сравнения картинок там нет — это проверки разметки. Каждый тест начинается с гвардии «зарегистрированы ровно те состояния, которые заводит нарезка», с зафиксированным порядком: состояние, добавленное мимо реестра, валит тест. Дальше идёт видимый контракт из спецификации — подписи, чипы, счётчики, наличие и отсутствие элементов. Большинство файлов рендерят в строку, несколько монтируют в jsdom, где нужна работа с фокусом и вводом. Общий тест по реестру проверяет уникальность идентификаторов и то, что каждое состояние монтируется и размонтируется без исключений на обоих языках — этим ловим пропавшие ключи словаря.
