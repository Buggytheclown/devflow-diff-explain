# Документация Шерпы

Источник правды — код. Документы здесь описывают то, что из кода не читается: зачем система устроена так, какие инварианты держатся, что решили и почему. Контракты (схемы, интерфейсы, константы) документы не дублируют: каждый ссылается на файл в `packages/protocol` или `packages/server`, где они лежат.

## Состав

| Документ | Что там |
|---|---|
| [`product.md`](product.md) | Продукт: проблема, принципы, словарь, главный экран, сценарии, функциональные требования, не-скоуп |
| [`architecture.md`](architecture.md) | Система: пакеты и роли, поток данных, хранилище, оркестратор маршрута, `ReviewHost` и `HostCapabilities`, нефункциональные требования, инварианты |
| [`protocol.md`](protocol.md) | Протокол сессия↔сервер: ограничения, CLI, задачи, очередь, живость, discovery, версии, таблица ручек |
| [`decisions.md`](decisions.md) | Журнал решений по подсистемам. Новое решение — новая запись здесь |
| [`testing.md`](testing.md) | Проверки, юнит-тесты, контракт-сьют хостов, e2e, перф-бюджеты, галерея состояний |
| [`design/`](design/) | Дизайн-хендофф: `README.md` (экраны, токены, модель состояния), `SPEC-elements.md` (поведение элементов, клавиатура), `SPEC-additions-2026-08-26.md`, `SPEC-onboarding-2026-09-02.md`, `SPEC-theming-2026-09-12.md`, прототипы `*.dc.html` |
| [`research/`](research/) | Разведки: API Арканума, Cloudia, API GitHub, Plannotator, difftastic, Pulldash, ожидание задачи в харнесах |

## Приоритет при конфликте

`product.md` → `design/SPEC-elements.md` → `design/README.md` → прототип `design/Devflow Diff Explain.dc.html`. Прототип — референс, не источник кода.

Если документ расходится с кодом, прав код — чинить надо документ.

## Как ссылаться из кода

Формат в комментариях — путь от корня репозитория и раздел: `docs/protocol.md §7`, `docs/design/SPEC-elements.md §2.6`, `docs/product.md §3`. Нумерация разделов в `product.md` и `protocol.md` стабильна: новый раздел дописываем в конец, в середину не вставляем.

## Стиль

Короткие абзацы, факты, числа. Без вводных («важно отметить», «стоит подчеркнуть»), без пересказа кода, без истории разработки: кто, когда и в каком порядке делал — в `decisions.md`, и только там, где это объясняет решение.
